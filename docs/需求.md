# LimitUpLab 需求说明

## V1 最终范围（2026-08-29）

V1 定义为一个使用完整收盘数据的首板复盘与次日一进二候选研究工具。它只处理已经结束的交易日，不承担盘中盯盘或实时交易终端职责。

V1 的核心闭环为：

```text
完整收盘数据
  -> 首板候选硬过滤
  -> 结构化 Facts 与可解释评分
  -> 不可变 Top10 次日观察快照
  -> D+1 首板到二板结果回填
  -> D+1 至 D+5 收益与风险追踪
  -> 预测复盘、质量审计和评分改进建议
```

V1 默认 Agent 可以回答最新或指定历史交易日的涨停池、首板评级、个股日 K、龙虎榜、指数区间走势、晋级率、Top10 追踪和评分复盘问题。所有事实必须来自本地完整收盘数据或可回放的结构化快照。

V1 明确不包含：

```text
盘中行情和分时盯盘
集合竞价决策
实时热股榜
实时板块行情
实时新闻或通用网页搜索
自动下单和交易执行
首板一进二以外的策略推荐
```

默认配置必须使用 `LIMITUPLAB_AGENT_PROFILE=v1_close_review`。实时热榜、板块、新闻、远端涨停池和网页搜索等已有扩展工具只允许在 `extended` 研发配置中启用，作为 V2 能力储备；不得出现在 V1 默认 Planner 的工具 Schema、Skill、Tool Policy 修复或执行链路中。

V2 再考虑接入稳定、授权明确的实时数据，扩展竞价或盘中场景，并在统一的预测快照、Outcome 和审计协议上增加更多策略。

## 最新范围变更（2026-08-25）

历史相似案例检索已从产品范围中移除。原因是结构化相似度难以形成可靠、可验证的业务定义，检索结果对首板推荐和复盘的增量价值有限，同时会显著增加计算、缓存和解释成本。

后续不再建设相似案例 API、相似度算法、案例卡片、Agent 检索工具或专用 K 线回填。已有首板特征与后续走势数据继续服务于评分、Top10 追踪、回测和 Evaluation Agent。本文后续出现的相关早期设计仅作为历史讨论记录，不再作为实现或验收依据。

## 项目新定位

LimitUpLab 不再只是“涨停复盘看板”，而是一个面向短线研究场景的：

```text
A 股首板质量评级与 Agent 复盘系统
```

核心目标是帮助用户在当日收盘后，从首板涨停股票中筛选出更值得次日观察的候选池。

系统不直接输出“买入/卖出建议”，而是输出：

```text
首板质量评分
评级
观察优先级
评分依据
风险标签
Agent 自我评价
```

定位可以表述为：

```text
基于真实涨停数据的可解释首板评级 Agent。
```

英文简历版：

```text
A facts-first LLM agent for explainable first-board stock rating and self-evaluation.
```

## 核心业务问题

用户关心的问题是：

```text
今天涨停的首板票里，哪些封板质量更好，次日更值得重点观察？
```

项目不依赖第二天集合竞价数据作为核心输入，因为实时竞价数据不稳定、难验证、难回测。

新的核心输入是：

```text
当日首板涨停数据 + 市场环境 + 行业热度 + 个股 K 线与扩展评分输入
```

## 核心用户流程

1. 收盘后导入当天涨停和炸板数据。
2. 系统筛选当日首板票。
3. Agent 为每只首板票构建结构化 facts。
4. 评分引擎给出首板质量分数和评级。
5. LLM Agent 基于 facts、score breakdown 和风险证据生成解释。
6. Critic Agent 检查评分是否过度乐观、是否缺关键数据、是否存在反向证据。
7. 前端展示首板评级列表。
8. 用户通过对话入口追问当日首板、个股评分、走势和风险原因。
9. Chat Agent 根据用户问题调用对应工具，基于结构化数据生成回答。
10. 次日数据回填后，Evaluation Agent 评价昨天评分是否有效，并生成反思和调参建议。

## 首板候选池定义

第一版候选池基础条件：

```text
trade_date = 最新交易日
board_height = 1
closed_limit = true
```

第一版候选池硬性过滤条件：

```text
排除 ST / *ST / 退市风险警示股票
排除北交所股票
排除科创板股票
排除新股/次新股
排除成交额过小样本
```

过滤原因：

```text
ST 股票交易规则和风险属性特殊，不适合与普通首板样本混合评分。
北交所和科创板涨跌幅制度、流动性结构和投资者门槛不同，第一版先排除。
新股/次新股的涨停行为容易受上市初期定价、流通盘和情绪因素影响，样本不可比。
成交额过小样本容易出现流动性失真，评分参考价值较低。
```

第一版可以先用可获得字段实现过滤；缺失字段要显式标记为 `data_missing`，并降低 `confidence`，不要让 Agent 猜测。

建议后续把过滤口径配置化：

```text
exclude_st = true
exclude_bse = true
exclude_star_market = true
exclude_new_stock = true
min_amount = 待回测确定
new_stock_days_threshold = 待回测确定
```

后续如需扩展，再区分 10cm / 20cm / 30cm 样本池，避免不同涨跌幅制度混合评分。

## 首板评分维度

第一版评分基于已有数据，可以拆成以下子项：

```text
1. 首封时间
   越早封板，评分越高。
   早盘首封优于午后首封。

2. 炸板次数
   炸板 0 次最好。
   炸板越多，封板稳定性越差。

3. 封板状态
   收盘封住加分。
   未封住大幅扣分。

4. 封板次数
   封板次数过多说明分歧较大。

5. 换手率
   过低可能流动性不足或一字板。
   适中较好。
   过高说明分歧较大。

6. 成交额
   过小流动性差。
   适中较好。
   过大可能资金消耗较高。

7. 行业热度
   同行业涨停数量越多，说明题材扩散更强。

8. 市场环境
   当日涨停数量、炸板率、连板高度、最高板高度。
```

输出评分时必须有子项拆解，例如：

```json
{
  "score": 82,
  "rating": "A",
  "score_breakdown": [
    {
      "name": "封板时间",
      "score": 24,
      "max_score": 30,
      "evidence": ["首次封板时间 09:36，属于早盘强封"]
    },
    {
      "name": "封板稳定性",
      "score": 18,
      "max_score": 20,
      "evidence": ["炸板次数 0 次，收盘封住"]
    }
  ]
}
```

## 评级体系

建议第一版：

```text
A: 强观察，80-100
B: 可观察，65-79
C: 中性，50-64
D: 弱观察，0-49
```

同时给出：

```text
confidence: 0-1
```

注意：

```text
score = 候选强度
confidence = 评分可靠性
```

高分不等于高置信度。

例如：

```text
评分 85，置信度 0.55
```

表示数据看起来强，但样本少、市场环境极端或关键数据缺失。

## Agent 的核心能力

这个项目要体现 Agent 开发能力，而不只是规则看板。

因此需要包含以下 Agent 能力。

## 1. Tool-Using Agent

LLM 不直接凭空回答，而是调用工具获取 facts：

```text
get_first_board_candidates(date)
get_candidate_facts(symbol, date)
get_score_breakdown(symbol, date)
get_market_context(date)
get_similar_cases(symbol, date)
get_stock_profile(symbol)
get_recent_news(symbol)
get_prediction_history(symbol)
get_today_first_board_summary(date)
get_stock_rating_detail(symbol, date)
get_industry_heat(date)
```

用户问：

```text
为什么这只股票是 A 评级？
```

Agent 流程：

```text
调用 candidate facts
调用 score breakdown
调用 similar cases
可选调用 stock profile / news
生成解释
```

## 2. Interactive Chat Agent：交互式问答入口

前端除了固定的评级展示页面，还需要提供一个自然语言对话入口。

这个入口不是普通闲聊机器人，而是建立在首板评级结果之上的 Tool-Using Agent。

用户可以询问：

```text
总结一下今天首板涨停的股票
今天首板里面质量最高的是哪些？
为什么 A 股票评分高？
A 股票有哪些历史相似股票？
A 股票主要风险是什么？
今天整体首板环境强不强？
把今天首板按行业归类
哪些股票评分高但置信度低？
评分最高的股票和历史案例有什么共同点？
```

Chat Agent 的处理流程：

```text
用户问题
  -> 识别意图和实体
  -> 选择工具
  -> 获取结构化 facts / 评分结果 / 相似案例 / 市场环境
  -> 组织回答
  -> 返回带事实依据和数据限制的解释
```

示例工具路由：

```text
问题：“总结一下今天首板涨停的股票”
调用：
  get_today_first_board_summary(date)
  get_first_board_ratings(date)
  get_market_context(date)

问题：“为什么 A 股票评分高？”
调用：
  get_stock_rating_detail(symbol, date)
  get_score_breakdown(symbol, date)
  get_similar_cases(symbol, date)

问题：“A 股票有没有历史相似股票？”
调用：
  get_candidate_facts(symbol, date)
  get_similar_cases(symbol, date)
```

回答要求：

```text
必须引用系统已有 facts
必须说明评分来自哪些维度
必须区分 score 和 confidence
必须说明相似案例的相似点和差异点
不能编造新闻、资金流、基本面或未提供的数据
不能输出买入/卖出/仓位/目标价建议
```

前端形态建议：

```text
主区域：首板评级表和详情
右侧抽屉或底部面板：Agent Chat
```

这样用户既可以快速扫描结构化结果，也可以围绕某只股票继续追问。

Chat Agent 是项目的关键展示点之一，因为它体现：

```text
自然语言意图理解
工具调用
结构化数据 grounding
可解释回答
上下文追问
安全边界控制
```
## 3. RAG：历史相似案例检索

最核心的 RAG 不是新闻，而是历史相似首板案例。

数据源来自自己的结构化历史库：

```text
limit_up_events
market summaries
first_board_features
next_day_outcomes
agent_predictions
```

每个历史首板样本都可以变成一个 case：

```json
{
  "symbol": "002xxx",
  "trade_date": "2026-06-01",
  "first_limit_time": "09:36",
  "break_count": 0,
  "turnover_rate": 8.2,
  "amount": 1200000000,
  "industry": "机器人",
  "market_failed_rate": 0.42,
  "market_limit_up_count": 88,
  "same_industry_limit_up_count": 6,
  "next_day_promoted": true,
  "next_day_high_pct": 10.0
}
```

检索目标：

```text
找到历史上结构相似的首板样本，并展示它们的次日表现。
```

## 4. 相似度计算方式

第一版不建议上向量数据库。

用结构化特征相似度更可解释。

相似度特征包括：

```text
first_limit_minutes
first_limit_bucket
break_count
seal_count
turnover_rate
amount_log
market_failed_rate
market_limit_up_count
continued_board_count
max_board_height
same_industry_limit_up_count
industry_event_share
recent_5d_return_pct
```

可以用加权相似度：

```text
similarity =
  0.20 * 封板时间相似度
+ 0.20 * 封板质量相似度
+ 0.15 * 换手率/成交额相似度
+ 0.20 * 市场环境相似度
+ 0.15 * 行业热度相似度
+ 0.10 * K线结构相似度
```

返回时要解释相似原因：

```json
{
  "similarity": 0.84,
  "reasons": [
    "首封时间同处早盘区间",
    "炸板次数均为 0",
    "市场炸板率接近",
    "行业热度接近"
  ]
}
```

## 5. 历史案例检索性能设计

不能每次全量扫描所有历史样本。

推荐：

```text
两阶段检索：SQL 快速召回 + Python 精排
```

第一阶段 SQL 召回：

```text
board_height = 1
closed_limit = true
trade_date < target_date
first_limit_bucket 接近
break_count 接近
优先最近 180 / 360 个交易日
LIMIT 300-500
```

第二阶段精排：

```text
对召回样本计算完整相似度
取 Top 5 / Top 10
```

后续可建表：

```text
first_board_features
```

字段包括：

```text
trade_date
symbol
first_limit_minutes
first_limit_bucket
break_count
seal_count
closed_limit
turnover_rate
amount_log
industry
same_industry_limit_up_count
industry_event_share
market_limit_up_count
market_failed_rate
continued_board_count
max_board_height
feature_vector_json
created_at
```

配合索引：

```sql
CREATE INDEX idx_first_board_features_date
ON first_board_features (trade_date);

CREATE INDEX idx_first_board_features_bucket
ON first_board_features (first_limit_bucket, break_count, closed_limit);

CREATE INDEX idx_first_board_features_industry
ON first_board_features (industry);
```

这样即使历史样本几万条，也可以保持响应速度。

## 6. 股票基本信息工具

需要，但不是第一优先级。

用于过滤和解释：

```text
是否 ST
上市板块
是否新股/次新
流通市值
总市值
所属行业
概念标签
涨跌幅制度：10cm / 20cm / 30cm
主营业务
```

工具可以是：

```text
get_stock_profile(symbol)
get_market_board(symbol)
get_concept_tags(symbol)
```

基本信息主要用于：

```text
样本过滤
评分归一化
解释增强
```

不应该成为短线首板评分的主导因素。

## 7. 新闻/公告/研报 RAG

需要，但放第二阶段或第三阶段。

优先级：

```text
公告 > 新闻 > 研报
```

原因：

- 公告更确定，比如重组、业绩、风险提示、异动公告。
- 新闻可以解释题材催化，但噪音大。
- 研报偏中长期，对首板次日晋级价值有限。

新闻/公告 RAG 应该用于：

```text
解释增强
风险提示
题材背景
```

不直接决定评分。

例如：

```text
评分来自封板质量和市场结构。
新闻只用于解释可能的题材催化。
```

## 8. Explanation Agent

用户问：

```text
为什么给某只股票 A 评级？
```

Agent 必须回答：

```text
评分拆解
关键事实
相似历史案例
风险点
置信度原因
```

不能回答泛泛而谈。

Explanation Agent 也要服务于对话入口。

例如用户追问：

```text
这个 A 评级和历史相似案例比，优势在哪里？
```

Agent 应该调用相似案例工具，并回答：

```text
当前样本在首封时间和炸板次数上更强，但市场炸板率高于相似案例均值，因此置信度需要下调。
```

好的回答示例：

```text
该股 A 评级主要来自三点：
1. 首次封板时间 09:36，属于早盘强封；
2. 炸板次数为 0，收盘封住，封板质量较好；
3. 所属行业当日有 6 只涨停，板块热度较高。

但需要注意，当前市场炸板率为 61%，整体接力环境偏弱，因此置信度为 0.72，而不是更高。
```

## 9. Critic Agent

评分后要有自检。

Critic Agent 检查：

```text
是否过度乐观
是否忽略市场退潮
是否缺失关键数据
是否有相反证据
是否违反投资建议边界
```

例如：

```json
{
  "critic_warnings": [
    "市场炸板率高于 55%，应降低高分样本置信度",
    "该股换手率偏高，说明分歧较大"
  ],
  "confidence_adjustment": -0.12
}
```

## 10. Evaluation Agent：自我评价闭环

这是项目的重要亮点。

Agent 每天记录自己的评分：

```text
agent_predictions
```

次日数据出来后，记录真实结果：

```text
agent_outcomes
```

再生成评价：

```text
agent_evaluations
```

评价标签：

```text
success
partial
miss
avoid_success
false_negative
```

例如：

```json
{
  "symbol": "002xxx",
  "prediction_date": "2026-06-01",
  "rating": "A",
  "score": 86,
  "outcome": {
    "next_open_pct": -8.5,
    "promoted_to_second_board": false,
    "next_close_pct": -9.2
  },
  "evaluation": "miss",
  "lessons": [
    "市场退潮时，封板时间权重可能过高",
    "应提高高炸板率环境下的风险惩罚"
  ],
  "suggested_changes": [
    "当 market_failed_rate > 0.55 时，将最终评分上限限制为 80"
  ]
}
```

注意：

```text
Agent 生成调参建议，不自动修改评分规则。
```

这样避免过拟合和不可控变化。

## 11. LLM 的正确位置

为了找 Agent 开发工作，项目需要接 LLM。

但 LLM 不直接打分。

正确架构：

```text
结构化 facts
  -> 规则/模型评分
  -> 历史案例检索
  -> LLM 解释
  -> LLM Critic
  -> Evaluation Agent
```

错误架构：

```text
行情数据 -> LLM -> 股票评分
```

LLM 应该负责：

```text
解释评分
回答追问
生成反思
总结相似案例
生成调参建议
```

其中“回答追问”必须通过工具完成，而不是直接让模型凭记忆或常识回答。

Prompt 约束：

```text
只能使用 provided facts / score breakdown / similar cases
不能编造数字
不能输出买入、卖出、仓位建议
不能承诺收益
必须说明数据限制
```

```text
次日表现评价
```

页面还需要包含对话入口：

```text
Agent Chat
```

支持围绕当前页面上下文追问：

```text
当日首板总结
个股评分原因
评分拆解说明
历史相似案例
行业热度
风险因素
过往评级复盘
```

Chat 面板不替代结构化表格，而是用于进一步解释和探索。

## 13. 网站化与 Agent 运行架构

如果项目从本地工具升级为网站，需要把 Agent 执行从“同步函数调用”升级为“可追踪、可并发、可恢复”的运行架构。

目标不是一开始就做复杂分布式系统，而是先把关键边界设计清楚：

```text
多用户并发请求
Agent 执行耗时
LLM 调用成本
历史案例检索重复计算
多轮对话上下文膨胀
任务失败和超时恢复
```

### 13.1 并发控制

网站化后可能出现这些并发场景：

```text
多个用户同时查看同一天首板评级
多个用户同时追问同一只股票
同一个用户连续发送多个问题
数据导入任务和前端查询同时发生
LLM Agent 执行时间较长，接口不能一直阻塞
```

推荐架构：

```text
前端请求
  -> FastAPI API
  -> 查询缓存 / 数据库
  -> Agent Run 记录
  -> 后台 Worker 执行
  -> 保存结果
  -> 前端轮询 / SSE / WebSocket 获取结果
```

第一版可以先做同步调用，但数据结构要预留异步化能力。

建议新增运行记录表：

```text
agent_runs
```

核心字段：

```text
id
session_id
user_id，可为空
run_type: rating / chat / critic / evaluation
status: pending / running / success / failed / timeout
input_hash
input_json
output_json
error_message
started_at
finished_at
created_at
```

用途：

```text
追踪每次 Agent 执行
复用相同输入的结果
排查失败原因
统计耗时和成本
为后续异步队列做准备
```

### 13.2 结果缓存

很多 Agent 结果在同一个交易日内可以复用。

适合缓存的内容：

```text
当日首板候选池
个股 facts
评分结果
历史相似案例 Top-K
市场环境摘要
行业热度摘要
```

缓存键可以基于：

```text
trade_date
symbol
run_type
input_hash
model_version
scoring_version
```

注意：

```text
评分规则版本变化后，旧缓存不能直接复用。
数据重新导入后，当日缓存需要失效。
LLM 解释可以缓存，但必须记录使用的 facts 版本。
```

### 13.3 连续对话上下文控制

Agent Chat 需要支持多轮追问，但不能无限把历史消息塞给 LLM。

上下文拆成两类。

会话状态：

```text
session_id
current_trade_date
current_symbol
current_page
last_intent
last_tool_result_refs
last_rating_id
```

消息历史：

```text
最近 N 轮用户问题和 Agent 回答
更早对话的摘要
关键实体和用户关注点
```

上下文控制规则：

```text
只保留最近 6-10 轮原文
更早消息压缩为 summary
工具返回的大 JSON 不直接塞进历史，只保存 result_id 或摘要
每次回答前重新调用工具获取最新 facts
当日期、股票代码或指代不清时，要求用户澄清
不同交易日和不同股票的上下文要显式切换
```

示例：

```text
用户：“它有没有历史相似股票？”
系统需要从 session state 中解析 current_symbol。
如果 current_symbol 不存在，则追问用户具体股票。
```

### 13.4 轻量 Multi-Agent 架构

项目需要体现 Multi-Agent 能力，但不应该让多个 LLM Agent 自由聊天。

推荐使用“轻量 Multi-Agent + 工具编排”：

```text
Coordinator Agent
  -> Facts Builder
  -> Rating Agent
  -> Retrieval Agent
  -> Explanation Agent
  -> Critic Agent
  -> Evaluation Agent
```

职责划分：

```text
Coordinator Agent: 识别用户意图，选择执行流程和工具。
Facts Builder: 从数据库构建结构化事实，不使用 LLM 编造数据。
Rating Agent: 基于规则/统计模型输出评分、评级、置信度和拆解。
Retrieval Agent: 检索历史相似首板案例并解释相似原因。
Explanation Agent: 基于 facts、score breakdown 和 similar cases 生成自然语言解释。
Critic Agent: 检查过度乐观、缺失数据、反向证据和合规边界。
Evaluation Agent: 在结果回填后评价历史评分表现并生成反思。
```

原则：

```text
确定性计算优先，LLM 只做解释、总结、批判和反思。
每个 Agent 都有结构化输入输出。
每一步都可以单独测试和回放。
不让 LLM 直接决定股票评分。
不让多个 LLM Agent 无约束互相讨论。
```

### 13.5 超时、重试与失败降级

Agent 执行需要可恢复。

建议规则：

```text
单次 LLM 调用设置超时。
工具调用失败时返回明确错误，不生成虚假答案。
历史相似案例缺失时，仍可展示评分，但降低 confidence。
LLM 解释失败时，前端展示结构化评分结果和失败提示。
同一任务失败可重试有限次数。
失败原因写入 agent_runs.error_message。
```

降级策略：

```text
LLM 不可用 -> 展示规则评分和模板化解释。
相似案例不可用 -> 展示“历史样本不足”，不强行类比。
部分字段缺失 -> 标记 data_missing，并降低置信度。
```

### 13.6 成本与速率控制

如果接入真实 LLM，需要控制成本。

策略：

```text
优先缓存同一日期、同一股票、同一问题类型的结果。
列表页不为每只股票自动生成长文本。
用户打开详情或主动追问时再调用 LLM。
批量总结使用压缩后的 facts，不传原始大表。
限制单用户并发 Agent run 数量。
限制单个 session 的连续请求频率。
```

### 13.7 生产化优先级

建议实现顺序：

```text
1. 单用户同步版首板评级
2. Agent Chat 同步版
3. agent_runs 记录和结果缓存
4. 会话上下文管理
5. 异步任务队列和 Worker
6. SSE / WebSocket 任务进度返回
7. 多用户权限、配额和限流
```

这个阶段的目标是让项目具备真实网站的架构思考，而不是为了复杂而复杂。
## 14. 项目最大亮点

最终亮点是：

```text
不是一个股票聊天机器人，也不是普通涨停看板，而是一个具备事实构建、可解释评分、不可变 Top10 预测、工具调用问答、LLM 解释、Critic 自检和次日结果自我评价的首板评级 Agent。
```

项目故事：

```text
数据 -> 评分 -> 检索 -> 解释 -> 对话追问 -> 自检 -> 结果回填 -> 自我评价 -> 规则改进建议
```

这条链路非常适合作为 Agent 开发求职项目。
