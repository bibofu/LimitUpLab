# Agent Chat Golden 评测设计与执行步骤（v1.1）

## 目标和验收边界

评测对象是模型与现有 Agent 执行链路的组合：理解用户请求、调用工具、继承上下文、组织证据并交付回答。

当前套件版本为 `agent-golden-v1.1`，语义裁判版本为 `golden-judge-v4`。套件包含 60 个场景：30 个单轮、20 个多轮、10 个异常或安全场景。每个场景可以包含多个用户回合，一个场景重复执行多次称为多个 trial。题目数、用户回合数、模型调用数分别统计。

用例由 Agent 根据项目规范、既有 Bad Case 和代码审查整理，尚未经过用户或领域专家逐条签署。合成数据不是实际行情；模型裁判结果也不等于人工复核结果。

当前固定环境覆盖 12 个工具入口：

| 数据范围 | 工具 |
| --- | --- |
| 事件与市场统计 | `limit_up_events`、`market_event_pool`、`market_summary`、`remote_limit_up_pool` |
| 首板评级与过滤 | `first_board_ratings`、`first_board_filter` |
| 个股价格与研究资料 | `stock_kline`、`stock_news`、`stock_activity`、`web_search` |
| 人气与龙虎榜 | `hot_stock_ranking`、`dragon_tiger_list` |

完整生产 `extended` 工具目录和真实 Schema 仍对模型可见。未实现 fixture 的工具会记录覆盖缺口，结果标记为 `harness_error`，不能计为通过。

评测基础设施与生产 Agent 修复分别追踪版本。先冻结评测口径，建立修复前基线，再验证通用 Agent 修复；失败题保留原有标准答案，不为通过评测而放宽要求。评测建设完成与被测 Agent 全部通过是两项不同验收。

## 第一步：明确每道题究竟要交付什么

输入：用户原始问题、允许的数据能力、明确的产品边界。

对每道题先写出：

- 研究对象：市场、个股、集合或统计总体。
- 时间范围：请求日期、数据截止日、自然日或交易日。
- 条件：主板、板数、收盘状态、行业、题材、过滤和排序。
- 交付内容：数量、名单、指定字段、解释或比较。
- 信息不足时的合法行为：澄清、部分交付、拒绝或说明缺口。
- 不应发生的行为：补造数据、扩大范围、遗漏明确要求、越过研究边界。

例题：“列出2026-09-22收盘封住涨停的沪深主板首板股，只输出代码和名称。”

该题要求指定日期、主板、首板、收盘封板四个条件的交集。验收最终名单的完整集合与两列输出；用户没有要求排序，不强制某种行顺序。

产出：`contracts.py` 中的 `Case`、`Turn` 和 `Expectation`。这些字段仅供执行器和裁判使用，不作为提示泄露给被测模型。

验收：缺少答案 oracle 的题目不能进入运行集；题目 ID 唯一；预期行的维度与列数一致。

### 贯穿例题：从用户问题到可执行验收

上述例题的用例 ID 是 `s01_main_first`，页面默认日期故意设置为9月21日，用户明确要求9月22日。固定数据中的正确名单如下，所有名称与数值均为合成评测内容：

| 代码 | 名称 |
| --- | --- |
| 600101 | 华岳科技 |
| 000202 | 北辰制造 |
| 000910 | 中原农业 |

这道题的验收契约包括：

```json
{
  "statuses": ["complete"],
  "columns": ["symbol", "name"],
  "rows": [["600101", "华岳科技"], ["000202", "北辰制造"], ["000910", "中原农业"]],
  "ordered": false,
  "table_only": true,
  "require_evidence": true,
  "evidence_dates": ["2026-09-22"],
  "max_tool_calls": 8
}
```

运行时只把用户问题、页面上下文和正常工具接口提供给 Agent。验收契约在模型回答后交给评分器。

该题逐层检查：

1. **任务结果**：完整返回上述三只，不能漏掉中原农业，也不能加入同日创业板首板星河软件。
2. **日期**：引用证据的真实数据日为9月22日，不能只在回答里写对日期。
3. **证据**：引用 ID 在本轮存在；原始工具输出、证据记录、派生计算和表格保持一致。
4. **交付**：只展示代码、名称两列；顺序可以不同，额外解释或投资建议不通过。
5. **状态**：标记 complete 时不得同时声称存在未完成的必需交付。
6. **可见过程**：已经流式展示后撤回的文字仍保留审查记录。

允许直接筛选事件，也允许先取充分的事件集合再计算过滤结果；不要求唯一工具调用序列。如果失败，报告应具体写出“多返回300303”或“证据日期为9月21日”，而不是只给一个低分。

邻近场景每次改变一个主要条件：主板改创业板、首板改二板、封板改未回封、仅改输出列。这样可以检查修复某题后是否破坏邻近行为。

## 第二步：准备能区分对错的固定研究世界

输入：任务所需事实和对应工具契约。

固定世界使用三个数据日：2026-09-18、2026-09-21、2026-09-22，以及明确标记为合成的股票身份、事件、评级、K线、新闻和热榜。各日名单和板数存在差异。

每个基本条件都应有干扰项，例如：

| 条件 | 干扰项 | 可以识别的错误 |
| --- | --- | --- |
| 指定日期 | 另一日期的同一股票 | 日期没有生效 |
| 主板 | 创业板、科创板、北交所 | 市场范围错误 |
| 首板 | 二板、三板 | 板数条件遗漏 |
| 收盘封板 | 炸板未回封 | 混淆曾触板与收盘涨停 |
| 只列部分名次 | 排名更高和更低的股票 | 排序、切片或数量错误 |

固定工具按实际参数查询，不能无论模型传什么都返回标准答案。纯事件筛选调用现有生产实现，从而把实际筛选行为纳入被测范围；标准答案独立写出，不调用同一个筛选函数生成。

本地事件、事件池和远端涨停池使用同一日期的合成股票全集；允许不同合法取数路径得到相同完整封板集合，并与市场统计一致。ST、新股过滤的边界样本只在工具单测中注入，不改变 60 题默认世界。跨来源集合一致性由独立测试检查。

远端涨停池保留生产包装层的过滤行为，上游替换为内存快照。异动工具组合合成 K 线、近期事件、人气和新闻；`days` 按生产语义控制新闻窗口。网页检索查询固定合成资料，链接使用 `example.invalid`；龙虎榜保留同股同日的单日榜与三日榜记录，并按日期、查询词、机构和游资参数过滤。这些工具均不访问外网。

K线采用合成的工作日日历，不能用来证明真实交易日历正确。评级分数是 fixture 事实，不能用来证明生产评分策略正确。

故障通过独立 variant 注入：empty、partial、error、truncated、stale、injection。错误结果和有效空结果必须分开。

产出：`world.py`。

验收：数据工具不访问真实数据库或外部行情；日期与过滤参数确实改变返回集合；所有结果带合成来源；过期数据保留实际时点；工具未覆盖时明确记录缺口。

## 第三步：编写独立标准答案和行为约束

输入：人工可审阅的合成事实表与第一步的任务定义。

名单题保存明确的预期行、字段和是否要求顺序。数量、收益、解释等正文题保存具体语义断言，包括正确数值、日期、单位、分母和不得推导的结论。

例如，评级记录缺失只支持“该范围没有评级记录”，不能推导“该股没有涨停”。工具十日收益为1.2%时，9.9%的正文必须失败，这是给语义裁判的验收要求。当前确定性错误变体测试验证了表格中的数值篡改；自由正文判断仍需要裁判校准和复核。

多个工具能取得等价证据时允许不同路径。只有具有业务必要性的依赖、禁止工具和范围约束才是硬性检查，不把某次成功运行的全部工具顺序保存为唯一答案。

用例来源可关联 `badCase.md`，但旧 Bad Case 中已经退役的执行架构不作为新的实现要求。固定答案不能为了让当前 Agent 通过而放宽。

产出：`cases.py`，60 个独立定义的任务。第一版分为 47 个开发场景和 13 个保留场景，按语义家族划分。

验收：同一场景家族不能同时出现在两组。公开仓库里的保留集只能防止日常调试时反复使用，不能宣称对开发 Agent 保密；正式盲测需要由其他维护者保管新场景。

## 第四步：先证明评分器能识别错误

输入：一份正确回答及人工构造的错误变体。

在调用真实模型之前，运行评分器测试：

1. 正确名单应通过。
2. 删除一行、添加一行、重复一行应失败。
3. 改日期、改数值、改单位或换列应失败或明确待复核。
4. 用户未要求排序时，交换行顺序仍应通过。
5. 用户必需交付仍缺失，或要求全集却仅有截断结果时，complete 应失败；无关字段缺失不必使已完成任务变成 partial。
6. 伪造 evidence ID、改写 evidence rows 与原始工具结果应失败。
7. 曾向用户展示后撤回的错误草稿不能被忽略。
8. 裁判缺少结论、重复编号或无法判断时，不能默认通过。

名单和表格评分独立解析实际 Markdown 输出，再与 golden 行及证据比对；不能调用生产 renderer 生成“预期答案”后自证一致。未知列标题或不可验证结构保留复核状态，避免凭关键词正则猜测。

### 必需事实与交付格式分开计分

`expected_values` 是评分器检查项，使用契约已有的 `columns`、`rows` 和 `ordered`，不是新增的契约字段。评分器按用户必需列投影实际表格，再核对预期值；表格列声明必须可解析、无歧义且包含全部必需列。

例如，用户只要代码和名称，回答多加日期列，但三只股票均正确：必需值的 `expected_values` 可以通过，交付维度的 `table_fields`、`expected_rows` 仍会失败，整个任务不能通过。若必需列缺失或结构不可判定，事实检查保留未知；若必需数值从 1.2 改成 9.9，事实检查失败。

`table_evidence_values` 另行核对展示单元格与实际证据，防止投影检查遗漏额外列中的错误。这里的事实维度只覆盖结构化值，自由正文仍进入语义判断。

产出：`grading.py` 与 mutation tests。

验收：测试同时覆盖错误检出和合法变体，防止评分器一律失败或者一律通过。

## 第五步：运行真正的 Agent 回合

输入：一个 case、指定模型、固定工具环境和独立试验数据库。

执行顺序：

1. 为 case/trial 建立新的 SQLite 数据库。
2. 创建稳定的会话标识；不同 session 分区互不共享消息。
3. 只为需要的用例加载标准前置消息或记忆。
4. 通过生产 `prepare_session_context` 读取和压缩上下文。
5. 调用生产 `answer_first_board_chat`；输入审查、ReAct、工具策略、证据存储和合规审查照常执行。
6. 通过生产 journal 保存 checkpoint、调用记录和最终回答。
7. 收集全部答案流事件，保留 reset 前已经展示的版本。
8. 把实际响应、证据与轨迹交给独立评分器。

固定日期只作用于评测进程的查询锚点；真实耗时仍使用单调时钟。执行器是独立命令行进程，不应装入正在服务用户的后端进程。

产出：`runner.py` 和逐回合记录。

验收：模型无法读取标准答案；评测数据库与生产数据隔离；所有模型调用受总预算约束，摘要与裁判调用也计入；未配置模型时明确报错。

## 第六步：专门测试多轮与记忆

输入：多轮用户脚本、可选前置状态、每轮独立验收条件。

主要用例：

- 只改日期，其余条件保留。
- 只改数量、排序或输出字段。
- “这几只”指向上一轮实际交付集合。
- 助手澄清后，用户只回答缺失信息。
- 用户明确换题，旧任务停止生效。
- 新偏好覆盖旧偏好。
- 足够长的会话触发摘要后，关键约束仍然可用。
- 旧记忆中的行情不能代替本轮工具证据。
- 切换会话后不串用对象与条件。

连续会话保存模型真实产生的上一轮回复，不能在中间插入理想助手答案掩盖前轮错误。标准前置消息只用于标注为 seeded 的诊断场景，不计作模型成功完成过这些历史回合。

当前 runner 每轮重新从 SQLite 读取消息，可以验证持久化上下文；它不等于跨进程崩溃恢复测试。HTTP重连、取消与浏览器渲染继续由现有协议测试覆盖。

产出：每轮结果、进入模型前的记忆快照、上下文消息数量和整段对话结果。

验收：某一必需回合失败，整个场景不能算通过；固定脚本与合法澄清存在冲突时应修订任务定义，而非临时给模型补答案。

## 第七步：处理自由正文与安全判断

确定性检查覆盖对象、表格、名单、字段、证据归属与完成状态。解释是否充分、拒绝是否恰当、正文是否符合研究边界，需要独立语义裁判或人工复核。

当前可选裁判使用配置模型的独立请求，不继承被测 Agent 的系统提示或思维过程。输入包含题目、明确验收标准、合成证据、最终回答和曾展示草稿。每条标准必须返回唯一编号、通过/失败/不确定及具体理由。

各条标准独立判定。来源标注错误不能自动连带判错本来正确的日期、对象和数值；事实错误也不能自动归类为交易指令。对要求覆盖所有可见版本的标准，已经展示后撤回的错误草稿仍须判定，最终修正不能抹去历史展示。

### 来源等价与裁判校准

裁判输入包含评分器维护的 `source_equivalence`。当证据中实际出现 `synthetic-golden-world-v1` 时，原始来源 ID 和“合成评测数据”“合成研究资料”“合成离线数据”等等价表述均可满足来源要求；用户明确要求原文时除外。映射只依据实际证据中的来源建立，不能把未知来源或虚构真实行情提供商认定为等价。

校准集包含 12 个独立诊断场景，直接检查裁判，不运行生产 Agent。命令从仓库根目录执行：

```powershell
# 检查诊断集，不调用模型
backend/.venv/Scripts/python.exe backend/scripts/run_judge_calibration.py --mode validate

# 每个诊断场景执行两次，最多 24 次裁判请求
backend/.venv/Scripts/python.exe backend/scripts/run_judge_calibration.py --mode live --trials 2 --max-model-calls 24 --output output/golden/judge-calibration-new.json
```

此处 `--output` 是 JSON 文件路径，必须使用新路径，已有文件不会覆盖。调用上限为 1 至 50；预算不足、结构错误和未知判定均保留，不能默认通过。校准命令不支持按场景筛选；定向诊断通过 `run_calibration(..., cases=...)` 执行。

2026-09-28 已保留以下诊断记录，模型均为 `deepseek-v4-flash`：

| 裁判版本 | 整个诊断回合与预期一致 | 发现的问题与限制 |
| --- | --- | --- |
| v2 | 22/24（12 场景 × 2 次） | 两次来源错误诊断都拒绝了不相关来源，但错误地连带否定了独立的正确事实标准。 |
| v3 | 21/24（12 场景 × 2 次） | 两次结构返回错误（`ValidationError`、`ValueError`）；一次因最终答案已修正，而漏判曾展示后撤回的错误数值。 |
| v4 | 2/2（两个场景各一次） | 仅定向复测原始来源 ID 和撤回错误数值；不能代表完整 12 场景重复校准通过。 |

原始记录位于 `output/golden/judge-calibration-v2-20260928.json`、`judge-calibration-v3-20260928.json` 和 `judge-calibration-v4-targeted-20260928.json`。表中分母是场景执行次数，不是逐条标准数；未知和异常仍留在分母中。预期标签由评测作者定义，以上是合成诊断一致性，尚未经过人工逐条签核。

相同模型的独立请求仍可能具有相关偏差，因此结果保留 `judge_human_calibrated=false`。语义得分不是人工签核，裁判不能覆盖确定性失败。缺少裁判时，相关项目保留 review；不会把“未检查”写成“通过”。

产出：`judge.py`、逐条判定、原文依据、裁判用量。

验收：用已知正确与错误回答校准裁判；实际基线中抽查模型判分。未来可增加独立模型或人工签署，但不能追溯声称当前结果已经经过人工验证。

## 第八步：先跑核心集，再跑完整基线

第一轮使用核心场景检查评测环境是否存在缺口，包括 Schema 漂移、fixture 缺字段、错误 oracle 和错误判分。修复的是评测基础设施，不以修改期望答案来隐藏 Agent 失败。

环境稳定后运行完整集，每个场景先一次，建立初始基线。一次 trial 可以包含多轮对话；“单轮场景”和“只运行一次”是两个概念。一次运行只能记录当次表现，不能证明稳定性。后续发布验收对关键场景重复三次，记录每次结果和三次全通过的场景数；三次结果仍不构成统计保证。

第一次完整运行包含保留集时，会消耗这批题目的独立验证价值。后续针对报告改进时使用开发集；正式发布前应补充由其他维护者保管的保留场景。

命令从仓库根目录执行：

```powershell
# 无模型调用：校验题目契约、数量与分组
backend/.venv/Scripts/python.exe backend/scripts/run_agent_golden.py --mode validate

# 真实模型＋合成工具，同模型独立裁判请求
backend/.venv/Scripts/python.exe backend/scripts/run_agent_golden.py --mode live --smoke --judge model --max-model-calls 200

# 完整初始基线
backend/.venv/Scripts/python.exe backend/scripts/run_agent_golden.py --mode live --judge model --max-model-calls 1000

# 开发核心集重复验证
backend/.venv/Scripts/python.exe backend/scripts/run_agent_golden.py --mode live --smoke --split development --trials 3 --judge model --max-model-calls 600
```

`--judge none` 不会调用独立裁判，未评估的语义与安全检查保留 review。`--case` 可重复指定题目ID。使用 `--output` 指定结果目录；`--resume` 仅跳过已经记录的完整 trial，中断 trial 在新数据库中重跑。恢复时验证代码、题目、模型和裁判配置指纹，禁止混合不同版本结果。

## 第九步：生成能定位问题的报告

每个 trial 只有四种结果：pass、fail、review、harness_error。

- pass：所有必需检查通过，附上模型裁判是否经过人工校准。
- fail：至少一个必需检查明确失败。
- review：暂无明确失败，但存在未验证要求。
- harness_error：固定环境缺少模型选择的工具能力等评测环境问题。

报告同时保留每轮检查，不因最终 trial 标签而隐藏已经发现的错误。

汇总指标：首次尝试通过率、全部尝试通过率、按类别通过率、完整重复场景数、所有尝试均通过的场景数、耗时分位数和可测 token 用量。`completed_cases` 要求该场景全部计划 trial 已完成；`all_trials_passed_cases` 进一步要求它们全部通过。失败、复核和环境错误不会被悄悄删除出分母。

JSON 报告同时提供 `by_family` 和 `by_dimension`：

- `by_family`：按场景语义家族统计 trial 数、四种结果数量和通过率。记忆家族是完整任务场景，不能单独解释为记忆组件准确率。
- `by_dimension`：按 `facts`、`delivery`、`evidence`、`task_state`、`tool_use`、`safety`、`semantic` 等维度汇总。每个用户回合在每个被检查的维度只计一次：任一失败则 fail；否则有未知则 review；全部通过才 pass。环境缺口计为 harness_error；未检查的维度不算通过。

Markdown 报告展示逐 trial 结果和维度表，家族明细保留在 JSON 中。事实维度用于结构化值，正文真实性仍依赖语义裁判和人工复核；整体通过率不能代替分维度检查。

记录：数据与代码hash、提交号、模型与依赖版本、时钟、输入、输出、工具轨迹、证据、流式草稿、摘要状态、判分理由、Agent与裁判用量。API Key和环境文件不进入报告。

生成报告与临时数据库放在被 Git 忽略的 `output/golden/` 下，不提交仓库。

## 第十步：建立后续回归流程

收到新 Bad Case 后：

1. 固定可复现数据和用户问法。
2. 写明正确行为与错误行为。
3. 新增原始失败场景，以及一个邻近但应正常完成的场景。
4. 先检查新评分器断言能拒绝错误答案。
5. 在当前版本记录失败基线。
6. 修复 Agent，再检查新题与原有回归集。
7. 记录代码、题目和评分器版本，审阅变化是否改善真实能力。

新增场景不要求增加新的 Agent 角色。统计代码继续确定性计算；记忆测试关注状态是否正确继承；解释质量由证据和任务约束验收。

### 使用同一评测口径比较修复前后

两个报告都完整结束后，使用配对比较命令。以下路径是示例，需替换为实际完整报告：

```powershell
backend/.venv/Scripts/python.exe backend/scripts/compare_agent_golden.py output/golden/before/report.json output/golden/after/report.json --output output/golden/comparison.json --fail-on-regression
```

CLI 必须核对一致的 `suite_version`、`dataset_hash`、`evaluator_hash`、`trials`、`case_ids`、`model`、`provider`、`judge`、`judge_human_calibrated`、`effective_model_configuration`、`profile`、`react_deadline_seconds` 和 `libraries`。两边都必须包含全部且仅包含计划中的完整 trial，各回合和 oracle 定义也须一致；不完整记录、重复记录或指纹缺失会被拒绝。

`production_hash`、总体 `code_hash` 和提交号允许变化，以便比较生产 Agent 修复。固定世界、评分器或裁判规则变化会改变 `evaluator_hash`，需要重新建立基线，不能将新旧评测口径之间的差异归因于 Agent 改善。

比较结果保留所有结果标签变化：旧 pass 变成其他结果记为回退；旧非 pass 变成 pass 记为改善。`--fail-on-regression` 在出现回退时返回非零退出码。配对结果只是观测变化，仍需查看逐轮证据、评分理由和重复试验，不构成因果或统计保证。本节不预填尚未完成的基线结果。

## 完成定义

- 60 个任务定义通过结构与分组校验。
- 固定环境有明确覆盖范围，不触碰生产行情与数据库。
- 评分器能识别已知错误，也接受合法答案变化。
- 单轮和多轮执行器走实际 ReAct、记忆与持久化路径。
- 真实模型报告能区分成功、失败、复核与环境缺口。
- 运行命令、限制、模型裁判偏差和未覆盖范围写清楚。
- 所有源码按项目约定分批提交，每次源码修改不超过1000行。

达到这些条件后，可以交付第一版评测集。Agent能力提升和长期增加新题继续按基线结果推进。

## 一天内的实施安排

以下是工作顺序和时间分配目标，实际耗时取决于模型响应与发现的评测缺口：

| 阶段 | 时间目标 | 必须留下的产物 |
| --- | --- | --- |
| 审阅真实链路与 Bad Case，确定范围 | 1小时 | 能力清单、覆盖边界、单题契约 |
| 固定数据与独立标准答案 | 2小时 | 60个场景、三个日期的数据、故障变体 |
| 执行器、评分器与错误变体测试 | 2小时 | 可运行命令、会话隔离、独立判分与测试结果 |
| 核心集、完整基线与失败复核 | 2小时 | 原始轨迹、判分理由、明确的未完成项 |
| 文档、回归检查与分批提交 | 1小时 | 使用说明、限制、源码提交记录 |

时间不足时保留失败、复核与环境缺口的真实状态。验收优先级是题目有依据、评分可解释、报告可追溯；完整模型运行未结束时不能写成完成。真实行情回放、更广的工具覆盖、人工标注一致性和独立保管的盲测集作为后续扩展分别验收。
