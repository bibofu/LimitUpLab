# LimitUpLab 面试题参考答案

本文逐题回答根目录 `interviewPre.md` 中的 100 道问题。回答以当前代码和本地数据为准，不把“已经编码”说成“已经验证”，也不把启发式评分说成有效预测模型。

截至 2026-09-01，本地最新事实是：完整后端测试为 `332 passed`，另有 `10` 个参数化子测试；首板因子诊断新增到 21 个 outcome-ready 交易日、307 个候选，但样本依然不足；近 10 个预测日 Top10 的成熟 D+1、D+3、D+5 缓存当前均完整。原题中的 17 个工具、14 条修复规则和 11 条评测等数字已经过时，当前 V1 profile 暴露 20 个工具，系统注册 20 个 capability、18 条 Tool Policy 修复规则，并有 121 条以上单轮真实 LLM 评测口径。

## A. 核心定位与研究边界

### A1. “研究工具”与 recommendation、official、live 是否名实不符？

是，这里存在真实的命名债务，不能只靠聊天回答末尾的一句免责来圆。`live` 在代码里原本想表达“真实前向快照，而非历史回算”，`official` 想表达“当天唯一不可变版本”，但 API 消费者会自然理解为正式交易推荐。更合理的结构是把它们改成 `forward_snapshot`、`canonical_snapshot`、`research_rank`，并在响应模型中强制包含 `research_scope`、`data_as_of`、`evidence_status` 和 `risk_notice`。当前部分响应有 disclaimer，但还没有统一做到结构层，因此我会把它作为未完成的产品合规项，而不是声称已经解决。

### A2. 研究工具为什么做 09:25 集合竞价终选？

这既是一次“时点一致性”工程实验，也是产品演示需求，不应包装成纯研究必需品。它验证了盘前草稿、09:25 后信息截止、不可变快照和后续复盘如何串成前向闭环，但对当前 V1 的收盘后研究定位并非必需。主线已经删除集合竞价终选运行代码，完整实现由 `v1.1.0` 标签保存；V1 每天收盘后固化首板一进二观察 Top10。面试时我会明确承认：竞价链路展示了实时工作流能力，但在数据可靠性和产品定位未成熟前不应进入正式结论。

### A3. Top10 是否事实上就是买入优先级？

它确实会影响用户注意力，所以不能说“加一句不构成建议就完全没有推荐属性”。我能做的实质区分是：系统输出的是基于收盘事实的研究排序，展示分数、缺失数据、反证和历史表现，不给具体买卖动作、仓位、目标价、预期收益，也不接交易执行。但排名仍有行为诱导风险，因此产品上应使用“观察池/研究排序”，把未验证状态和基准比较放在排名同一视觉层级。合规边界来自产品行为和结构化风险信息，不来自一句免责。

### A4. “Lab”这个名字还诚实吗？

我认为仍然诚实。Docker、HTTPS、备份和限流说明实验系统具备可靠运行能力，不等于它已经成为交易系统；“Lab”强调的是评分假设仍在持续证伪、Challenger 未通过门槛、模型没有自动下单。不过，如果未来接入实盘并向用户售卖明确交易信号，就必须重新命名并重新审视牌照、适当性和风险披露，不能继续用 Lab 回避产品实质。

## B. 统计与量化方法

### B5. 一边严谨证伪旧规则，一边继续写新手工规则，是否矛盾？

矛盾成立，除非把新规则严格定义为“待验证假设”。当前新规则的合理身份只能是候选召回、可解释排序和 Challenger，不能因为代码写完就宣称有效。诊断模块的结论应反向约束开发：新规则必须版本化、保存 point-in-time 输入、跑相同的日期阻断和基线比较，并在未达门槛时保持 shadow。项目的价值不应是不断增加规则，而应是让任何新直觉都进入可证伪流程。

### B6. 如何区分统计功效不足与真无信号？

现在不能区分，只能说“目前没有稳健证据”。以 20 个独立日期做一个简化的双侧符号检验直觉，在 Bonferroni `alpha=0.00357` 下至少需要 17/20 天同方向才显著；即使真实正向概率是 70%，检出功效也只有约 10.7%，80% 时也只有约 41.1%。这说明当前检验很容易假阴性。正确补充是预先定义最小有意义效应，做按日期的功效模拟和置信区间，展示“哪些效应当前有能力排除”，并继续积累到至少 60 个完整结果日。当前本地已到 21 日、307 个样本，仍然远不足以把无证据写成无信号。

### B7. `sector_relay` 稳定负 IC 是否说明方向标反？

这是首要调查假设，但不能看到负 IC 就直接翻转权重。负向可能来自代码方向错误，也可能说明强板块在该样本期更拥挤，或者“次日开盘到收盘”这个 outcome 惩罚高开后的兑现。我的处理顺序应是：检查因子构造和缺失填充；画逐日分箱与单调性；检查不同市场状态；分别跑原方向、取反和移除因子的前向 Challenger；最后只用未参与调参的日期判断。当前我会诚实说“怀疑方向或 outcome 解释有问题，尚未完成验证”，不会悄悄把它翻转成新规则。

### B8. Lasso 的 `alpha_fraction=0.1` 稳健吗？

不稳健，当前固定 0.1 只是诊断超参数，不是经过选择的最优值。我用 2026-09-01 本地 21 个结果日重新做了不落库的敏感性检查：`0.05` 保留 11 个因子，`0.1` 保留 7 个，`0.2` 保留 4 个；对应 blocked OOS R² 约为 0.029、0.044、0.059，但平均日 IC 的 p 值都不显著。由此能保留的稳健结论只是“未发现联合稳健信号”，不能把“具体保留了几个因子”当结论。后续应报告 alpha 路径，并用嵌套日期交叉验证或 one-standard-error 规则选惩罚。

### B9. 因子取值相同会怎样污染 IC？

当前实现对 ties 使用平均秩，整列常数时返回 `None`，该日期不进入这个因子的 IC。原 20 日报告中，有效日期从 `market_context=0`、龙虎榜/人气 11 日、结构类 12 日，到首封时间/成交额 20 日不等，所以准确表述不是“14 个因子都在 20 天无信号”，而是“13 个具备一定日期内变异的因子未通过当前门槛，另有因子无法评价”。目前报告还缺少逐日 `eligible/total` 比例，这是应该补的可观测字段；否则样本数 297 会掩盖某因子实际只有 11 个有效日期。

### B10. 为什么用 Bonferroni 而不是 BH？

最初选择 Bonferroni 是为了治理层优先避免假阳性，因为项目最危险的错误是把噪声晋升为评分权重；但它在相关因子和小样本下确实过度保守。更完整的报告应同时给出未校正 p、Bonferroni family-wise 结论和 BH-FDR 敏感性结果，并展示因子相关矩阵。生产晋升可以继续采用保守门槛，研究发现则可用 BH 生成候选假设。选择 Bonferroni 是风险偏好，不代表它是唯一正确统计答案。

### B11. `bootstrap_max_retention=0.995` 应如何解读？

第一反应应是红旗，而不是“非常稳定”。它表示至少一个因子在当前弱惩罚下几乎每次都被保留；同时 0.1 alpha 的旧报告保留 11/14，说明 Lasso 稀疏选择能力很弱，接近带轻微收缩的多元回归。它不等于所有因子都有 99.5% 保留率，也不严格等于 OLS，但足以否定“Lasso 已经筛出少数稳定因子”的说法。应增加 alpha 路径、系数符号稳定率、嵌套验证和更强惩罚；在此之前，bootstrap 保留率只作诊断，不作有效性证据。

### B12. OOS R²=0.014 有实用价值吗？

作为预测模型，当前没有足够实用价值。它只解释约 1.4% 的样本外波动，而且平均日 IC 不显著；不能据此支持 Top10 具备稳定收益优势。它的现阶段价值是工程和认识论上的：阻止系统把样本内相关包装成有效模型，迫使每次改权重都接受基线和样本外检查。真正的业务价值必须由 Top10 相对全池晋级 lift、收益、回撤、大跌率和跨市场状态稳定性证明，不能用“R²虽然低但金融都低”搪塞。

### B13. 随机种子和 4096 次置换的精度问题怎么处理？

固定 seed 保证同一输入可复现，但不保证 Monte Carlo 误差很小。4096 次随机符号翻转的最小步长约为 `1/4097`，在 `p≈0.004` 时抽样标准误也约千分之一，因此报告四位小数是机器输出精度，不是四位有效统计精度。20 个日期时完整枚举只有 `2^20≈105 万` 种符号组合，完全可以做 exact test；日期再多时应增加置换次数、报告 Monte Carlo 置信区间并跑多 seed 稳健性。

### B14. 从未真正晋升过的 Champion/Challenger 有什么价值？

它当前证明的是“系统知道什么时候不该改”，不是“自动学习已经成功”。版本绑定、不可变预测、日期 walk-forward、基线比较和显式批准闸门已有单元测试，也真实地产生过“Challenger 不晋升”的结果；但从未有候选在 60 个完整结果日后通过晋升，所以正向治理路径尚未被真实数据验证。面试时我会把它叫作已实现、未完成经验验收的安全机制，并把第一次真实晋升或长期拒绝都视为后续里程碑。

## C. LLM Agent 工程

### C15. 整条 Agent 链路的瓶颈在哪里？

最大瓶颈通常是两次串行 LLM 调用，其次是同花顺、新闻、K 线等外部 I/O，Tool Policy 的规则计算几乎可以忽略。移除重复 Skill 目录后，当前 V1 planner 系统提示实测为 16,165 字符，比此前文档记录的 17,420 字符减少约 7.2%，但每次仍会全量发送，规划本身仍有延迟和固定输入成本。如果只能继续优化一处，我会按业务域动态暴露 capability/tool schema，缓存稳定前缀，并为单能力高置信问题使用较小 planner；随后再并行无依赖工具并建立 p50/p95/p99 分段指标。

### C16. 工具调用 cap 会怎样影响复杂问题？

Planner 原始工具调用经过归一后，再由 Capability Contract 把 required tools 放到最前，总上限是 8。超过 8 个时后面的探索性调用会被截断，目前不会自动拆成第二轮，也没有给用户完整的“哪些证据被舍弃”提示。因此复杂组合问题可能得到最低证据充分但不够丰富的回答。现有测试覆盖合并顺序和必要工具补齐，但还缺系统化的 `7/8/9` 调用质量退化评测；更合理的方案是依赖图、预算感知规划和分阶段执行。

### C17. 举一条 Tool Policy 修复规则及其假阳性风险。

例如“今天市场环境如何”要求 `market_summary + market_index_trend + sector_performance + hot_stock_ranking`。Planner 只选涨停统计时，Policy 会补齐另外三类事实，修复“用一个局部指标概括全市场”的 failure mode。误触发的代价是额外延迟、token 和过度展开，所以 `market_environment` 与单纯“指数走势”被拆成不同 capability，并有“不应扩展”的负例测试。当前有规则互斥、空计划、缺失日期和多类修复测试，但还没有用真实线上分布统计每条规则的假阳性率，这是缺口。

### C18. post-hoc recompute 的触发条件是什么？

它不是通用幻觉检测器，只校验少数可确定证明的答案契约：完整涨停名单是否包含每个 symbol、位置分类是否覆盖完整分组、热股 TopN 是否齐全、热股与涨停交集是否精确、晋级统计是否包含关键分子分母，以及输出是否含禁止交易措辞。不满足时，用同一工具 facts 生成确定性模板。这个判断对“集合完整性”较强，对语言质量和一般事实幻觉无能为力；误判代价是把一段可读的回答换成较生硬模板。更重要的现存缺口是流式 delta 可能已经发出后才做最终校验，已发送文本无法撤回。

### C19. LLM provider 挂了，用户看到什么？

Planner 失败时，系统会尝试确定性路由和旧兼容路径；最终回答 LLM 失败时，会直接基于已取得的工具 facts 使用模板回答；既无 LLM 又无可用事实时，返回明确的“抱歉，该问题无法回答”，而不是空内容。Provider 重试默认最多 2 次。相关故障路径有单元测试，但降级回答的覆盖面不等于正常 LLM，开放式解释会明显变机械，所以还需要在 UI/监控中区分 provider outage，而不是让用户误以为系统正常。

### C20. Explanation、Critic、Review、Evaluation 有什么区别？

Explanation 把单个评分及证据翻译成人话；Critic 对同一个评分寻找反证并建议降低置信度，但不改原分；Evaluation 把持久化预测与 D+1/D+3 结果做确定性标签；Review 汇总多个日期 Top10、市场基线以及好坏样本特征。它们并不是四个平级裁判，也不会投票决定分数：确定性评分和不可变 outcome 是事实源，Critic/Review 只是不同粒度的解释。当前 Critic 是规则服务，Evaluation 也是确定性逻辑，Review 才可选用 LLM 总结，因此不是每次聊天都产生四次 LLM 调用。

### C21. 为什么 ContextVar 能修复 `os.environ` 的并发污染？

`os.environ` 是进程级共享可变状态，一个请求在 try/finally 中改值时，其他线程和协程都会看到；finally 只能恢复最终值，不能隔离重叠执行。`ContextVar` 的值属于当前执行上下文，async task 创建时会复制上下文，set 会返回 token，reset 只恢复当前上下文，因此并发任务互不覆盖。需要注意它不会无条件传播到任意手工新线程；如果跨线程执行，要明确复制 context 或在目标线程内设置。当前 override 位于每次 Agent 执行上下文中，避免了评测修改真实 chat 的进程全局配置。

### C22. 评测集是否有代表性？

原来的 11/11 已经扩展：基础单轮 fixture 有 18 条，改写集有 14 个语义家族、135 条消息，多轮有 10 个场景、20 个上下文 turn；2026-08-30 还运行了真实 DeepSeek 的 121 case 三轮稳定性和 10 个多轮场景。它们覆盖市场、涨停池、热门股、新闻、个股、评分、复盘和上下文交叉，但仍是开发者设计的分布，不能代表所有真实用户。最容易“评测全绿、线上仍挂”的是新实体歧义、混合约束、外部源异常和从未见过的口语改写。防止过拟合的下一步是匿名失败样本回流、独立 holdout 和按 capability 报告混淆矩阵。

## D. 系统设计与扩展性

### D23. SQLite 能支撑 4 个 worker 吗？

当前连接层已启用 WAL、外键、5 秒 busy timeout、NORMAL sync、自动 checkpoint、有限指数退避重试，并用 `PRAGMA user_version + BEGIN IMMEDIATE` 串行化 schema 初始化。这改善了多读一写和短事务冲突，但 SQLite 仍然只有一个写者；4 个 worker 下，预测落库、会话写入、usage 记账和日更重叠时仍可能锁竞争。此外限流器是进程内状态，4 worker 会把全局并发上限放大。低流量单机可以压测后使用，多实例或稳定并发上线应迁移 PostgreSQL，并把限流/锁放到 Redis 或数据库原子计数。

### D24. 无状态 HTTP 如何维持会话，长会话会不会撑爆 SQLite？

浏览器持有 HMAC 签名的匿名 owner cookie；`chat_sessions`、`chat_messages`、`chat_session_memories` 和 `agent_runs` 按 `owner_id/session_id` 持久化，HTTP 请求本身仍无状态。当前上下文采用 Session Memory：保留最近 8 条原始消息，尚未达到刷新批次的旧消息继续随请求携带，每累计 8 条旧消息便通过 `update_session_memory` Function Call 更新滚动摘要和结构化状态；LLM 不可用时确定性降级。`last_message_id` 是增量游标，摘要与原始窗口合计仍有硬上限，因此 prompt 不随历史线性增长。数据库中的完整原始消息仍会增长；目前支持列出、恢复、重命名和永久删除，但还没有自动 TTL、归档压缩或每用户容量上限。公开增长后仍需要消息保留策略、索引监控和按 owner 的存储配额。

### D25. 为什么命中已有竞价快照还要写库？

该问题属于 `v1.1.0` 集合竞价实验：当时为了故障恢复，命中不可变竞价快照后会用 `replace=True` 补写派生的一进二批次，导致看似 getter 的路径产生写副作用。业务动机可以解释，接口设计仍违反最小惊讶原则。当前主线已删除整条竞价运行链路；如果未来从标签恢复，必须将恢复动作放入显式作业编排，并保证纯 `get` 永不写库。

### D26. 多个 Repository 为什么共享一个 SQLite 文件？

共享文件的优点是部署简单、备份一致、跨表审计方便，并且 prediction、outcome、policy、usage 能在同一事务边界内维护。分成多个 SQLite 文件会降低某些写冲突，却失去原子性并增加备份恢复复杂度，而且并不能解决每个文件单写者的本质。目前有并发初始化和锁重试测试，但没有足够的多 repository 持续负载基准。真正需要扩展时，优先迁移 PostgreSQL，而不是靠拆 SQLite 文件延迟问题。

### D27. 两个 ThreadPoolExecutor 会泄露线程吗？

当前两处都使用 `with ThreadPoolExecutor(...) as executor`，函数退出时会 shutdown 并等待任务，正常路径和异常路径都不会永久泄露线程。代价是每次刷新都创建线程池，存在创建开销、外部连接峰值和慢任务拖住整个上下文的问题。收集器里的 HTTP session 生命周期也需要各自保证关闭。长期方案是一个受控的应用级 I/O executor 或异步客户端，加每源并发、超时和熔断，而不是继续在请求路径临时扩线程。

### D28. `/api/agents/eval` 在生产是否受保护？

现在受 `X-LimitUpLab-Admin-Key` 保护。除 `/eval` 外，评分策略、优化、数据健康、系统健康、日更状态、质量审计、因子诊断、运行轨迹和 usage 都使用同一 admin dependency；生产缺失强 admin key 会拒绝启动，未配置的开发环境调用管理接口返回 503。风险仍在于单个静态 key 缺少角色、审计主体和独立限流，后续应接真正的管理身份或至少反向代理层 IP allowlist。

## E. 数据工程与质量

### E29. AKShare 改字段或限流时会怎样？

当前闭板接口直接按中文列名取值，字段变更会抛 `KeyError` 并使主流水线失败；炸板接口异常目前被捕获后降级为空列表，这避免整批失败，但存在“误以为当天没有炸板”的静默风险。系统有日更状态、原始数量和后续数据健康检查，但 collector 入口还没有显式 DataFrame schema/version 校验。应为每个源定义 required columns、类型和合理范围，失败时标记 source status，而不是把失败转换成业务空集；同时保存原始响应摘要和备用源对账。

### E30. 最近 outcome 回填是否完整？

我不会凭日期口头猜。2026-09-01 本地完整性程序的实际结果是：最近 10 个预测日共 100 个 Top10；成熟的 D+1 为 90/90、D+3 为 70/70、D+5 为 50/50，`missing_case_count=0`，9 月 1 日自身仍是 pending。这份检查按本地交易日精确对齐，不用“下一根可用 K 线”冒充缺失日期，并进入数据健康和日更报告。如果过去三天回填失败，状态会变成 partial 并列出具体日期和 symbol；诊断只应消费 readiness 为真的 outcome。

### E31. 过滤阈值怎么定，如何控制幸存者偏差？

原题的 1 亿已过时，当前首板入池最小成交额是 5000 万，另外排除非首板、未封住、ST/退市风险、北交所、科创板、上市未满 120 天或明显新股标记。它们主要来自产品范围和流动性风险控制，不是已被严格实证的最优阈值，所以不应叫“模型发现”。控制选择偏差的方法是保留完整原始池和每只股票的 `filtered_out` 原因，并在离线诊断中对 3000 万/5000 万/1 亿、60/120 天等阈值做敏感性分析；如果只保存入池样本，就无法知道被过滤股票是否更好。

### E32. 三日 outcome 跑过吗？

我刚用当前本地数据运行了三日开盘到收盘口径：19 个成熟交易日、248 个候选，结论仍是 `no_robust_signal`；blocked OOS R² 约 0.0015，平均日 IC 约 0.147，但 p≈0.092，不显著，最强因子仍是 `sector_relay`。它没有推翻次日口径，但样本比次日更少，不能视为最终稳健性证明。后续还应预注册晋级、D+1、D+3 收益和回撤等多个目标，避免看完结果再挑最好口径。

### E33. volume 除以 100 是 hack 还是有依据？

它有市场数据单位背景：部分快照以股计，历史 K 线以手计，理论比例约 100；但“差 20 倍就除 100”仍是启发式，不足以证明一定是单位问题。当前实现利用历史 bars 的数量级做归一，应该进一步要求比值接近 100 的容忍区间、记录 `volume_unit_correction` 和原始值，并与成交额/价格反推量交叉验证。误修正会直接污染量比、放量判断和 discovery 排名，所以无法确认时宁可标缺失并降低置信度。

### E34. discovery 排除已涨停股票，究竟预测什么？

当前这条链路已经改名为“低位挖掘”，目标不是从当日涨停池评分，而是从热门题材和新闻召回尚未涨停的全市场股票，再用财报和 60 日 K 线寻找低位趋势启动观察样本。旧 `first-board-discovery-v2` 的 outcome 是“目标日是否收盘首板”，正样本来自候选在下一交易日成为首板；当前 `low-position-discovery-v3` 不再承诺“次日首板 Top10”，因此需要重新定义趋势启动、区间收益和回撤的独立 outcome。若继续称它为首板预测，原题批评完全成立。

## F. 诚实性与 claim 验证

### F35. 敢不敢现场跑测试？

敢，但必须先说清环境和测试层级。当前完整后端运行结果是 `332 passed` 加 `10` 个参数化子测试，前端生产构建也通过；README 顶部仍写 319，说明文档数字已经漂移，面试时应以现场输出为准并修正文档。外部真实 API 和真实 LLM 不应混进默认单元测试，否则网络波动会让回归不可重复；它们应作为单独的集成/验收套件。现场失败时我会先分类为代码回归、平台差异、外部依赖还是本地脏数据，而不是用“在我机器上能过”回避。

### F36. 评分 v3 “已完成”是什么意思？

只表示工程闭环完成：版本化策略、walk-forward、基线比较、Challenger、晋升门槛和审计接口都已实现；不表示 v3 已经证明比 v2 好。已有审计显示 Challenger 尚未满足 60 个结果日和测试日门槛，题材原因增强版本在同口径上甚至弱于当前版本，因此保持 shadow 并拒绝启用。更准确的文案应是“v3 治理实现完成，预测有效性未通过验收”，把 implementation status 与 evidence status 分开。

### F37. Tasks 里的“已完成”可信么？

目前 Tasks 大多把代码、测试和一次本地实测写在同一条下，但 `[x]` 的语义仍容易混合“实现完成”和“业务验证完成”。我不会现场逐个复述一个动态文件的勾选数量；更好的治理是每项拆成 `implemented`、`automated_verified`、`data_validated`、`production_observed` 四个状态，并链接测试或报告。像 Agent 路由、备份脚本可以说代码与测试完成；像评分准确性、治理晋升、真实用户泛化只能说仍在验证。

### F38. “当前无稳健信号”有没有在用户界面同等突出？

过去前端曾有预测质量审计面板，后来为了用户界面简化被移除；这造成首页排名比无信号结论更显眼，批评成立。管理 API 和 README 有完整结论，但普通用户不一定看到。正确做法不是把复杂统计全塞回首页，而是在盘前研究排序旁固定展示 evidence badge，例如“研究规则，21 个结果日，尚未验证优于基线”，并可展开查看审计。风险状态必须与分数同屏，而不是藏在文档或后台。

### F39. 记录问题但不修，有什么意义？

评审文档只有在转化为优先级、测试和提交后才有价值。项目已经据评审修过 ContextVar 并发污染、内部接口保护、SQLite 并发、AI 子串误匹配、真实 LLM 评测等问题；但 getter 写副作用、magic numbers、前端单文件和结构化免责仍未完全处理。面试时我会把评审分成“已修”“有意接受”“待修”，并说明为什么排序。知道问题到修复之间隔着风险评估、资源和可验证验收，不应隔着无限期文档展示。

### F40. 文档说转验证，代码却继续增长，怎么解释？

这段执行确实没有完全遵守“停止堆功能”的承诺。一部分新增代码是在补闭环所需的 outcome、诊断、权限、真实评测和数据完整性，不只是 UI 功能；另一部分确实是产品范围继续扩张，例如低位挖掘、新闻和竞价实验。我的复盘是范围控制失败：应该冻结 V1 capability，先让 60 日验证和真实用户反馈跑起来。当前已经删除集合竞价运行链路、历史相似案例和两套重复前端评测面板，并缩小 V1 profile；下一阶段仍应继续删除和拆分，而不是以 LOC 当进度。

## G. 代码细节

### G41. `ai` 子串误匹配修了吗？

原问题成立过，现在已修。ASCII alias 使用 token boundary 正则，`chairman` 不再因为包含 `ai` 而匹配 AI；测试明确断言 “The chairman discussed quarterly results” 不匹配，而 “AI 视频生成模型发布” 和“人工智能视频应用”匹配。尚未完成的是在真实新闻集上量化 precision/recall，当前只能证明这个已知假阳性被回归测试覆盖，不能声称整个题材匹配器准确。

### G42. 竞价涨幅 ≥9.5% 为什么给 0 分？

规则意图是惩罚接近一字涨停时的可参与性和换手验证缺失，不是断言这类股票后续表现一定差。9.5% 是主板接近涨停的经验边界，缺少本项目数据支持，因此只应是 `v1.1.0` 历史竞价实验的风险启发式。当前主线已删除该实现；若未来恢复，必须区分一字封单强度、是否开板、市场制度和可执行价格，并对阈值做前向分箱验证，不能沿用单一 9.5 阈值。

### G43. `_recall_score` 的 4、24、3 从哪来？

它们是人工构造的形状参数：以约 4% 当日涨幅为中心，给动量项 24 分上限，每偏离 1 个百分点扣 3 分，目的是避开太弱和接近涨停的样本。没有比经验更强的实证依据，所以我不会称它们为学习出的参数。当前低位挖掘 v3 已把终排重点转向题材、催化和 60 日结构，但类似 magic numbers 仍存在。正确处理是把常量集中成版本化 policy，跑分箱、扰动和前向 outcome，而不是逐个编故事。

### G44. `AUCTION_BASE_WEIGHT=0.8` 为什么？

它让盘后基本分主导，竞价只做最高 20 分的有限修正，设计上是避免 09:25 单点噪声完全推翻上一日结构；不是数据学习出的最优权重。0.5 会显著放大竞价，0.9 则几乎不重排。项目没有形成完整的 0.5/0.65/0.8/0.9 Top10 稳定性和 outcome 对比，因此不能辩称 0.8 最优。该参数随竞价运行链路从当前主线删除；若从 `v1.1.0` 恢复，应预注册权重网格并只在前向验证集选择。

### G45. 两套 A/B/C 阈值为什么不一致？

这是 `v1.1.0` 历史模块的语义漂移，不是一个值得保留的精妙设计。基础首板评分用 `80/65/50`，竞价终选用 `85/75/65`，导致同一字母跨页面含义不同。当前主线删除竞价实现后只保留一套评级映射；若恢复第二种研究排序，必须使用不同名称或显式携带 `rating_scale_version`，不能复用 A/B/C 制造跨页面歧义。

### G46. discovery confidence 的 0.52、0.82、1/300 合理吗？

这些数字只表达“数据覆盖度”，不表达“预测正确概率”：60 根 K 线让结构特征更完整，所以从 0.52 增至 0.72，上限 0.82 避免显示确定性。但字段名 `confidence` 很容易被误读为命中概率，而当前无信号诊断更说明不能这样解释。应改名为 `evidence_completeness`，由明确的字段覆盖和源新鲜度计算；模型可信度需要校准曲线或保序回归得到，不能用 K 线根数手写。

## H. 测试与质量保证

### H47. 合成测试和真实数据测试各证明什么？

绝大多数 `pytest` 是确定性单元/集成测试，使用合成事件、fake collector 或固定 LLM payload，主要证明过滤、路由、持久化、并发和统计代码按契约运行；它们不证明评分在真实市场有效。真实数据证据来自独立的本地诊断、outcome 完整性、DeepSeek 评测和部署验收，不应混成“332 个测试证明模型准确”。目前没有一份精确的 synthetic/real 测试数量分类，这是文档缺口；更成熟的测试报告应按 code correctness、data contract、provider integration、business validation 四层统计。

### H48. 只有强 planted signal 测试够吗？

不够。强单调信号只证明统计实现不会在明显信号下完全失灵，还需要弱信号功效曲线、纯噪声假阳性、方向反转、相关因子、缺失和 ties 等测试。尤其应模拟 20/40/60 个日期下不同 IC 和波动，报告检出率而不是单次 pass/fail。当前真实报告已诚实暴露低功效，但自动测试对假阴性的覆盖仍不足，这应当列为统计模块的下一项质量工作。

### H49. Windows 开发、Linux 生产有哪些风险？

已知差异包括 chmod、路径分隔、文件锁、默认编码、时区、进程启动方式和 shell 脚本。备份权限测试现在只在 POSIX 验证 mode，Windows 只验证内容；Docker/Linux 才是部署基线。当前测试在 Windows 本地通过，容器构建和真实 Ubuntu 服务器也跑过，但还没有正式的双平台 CI matrix，因此仍可能出现 Windows 绿、Linux 红。应在 GitHub Actions 至少跑 Ubuntu + Windows 的核心测试，并在 Linux 跑 Docker Compose smoke、备份恢复和时区用例。

### H50. 测试有没有跑真实 LLM？

默认 `pytest` 不调用真实 LLM，这是为了可重复和成本可控；它通过 fake/observed provider 测原生 `submit_agent_plan` Function Call、旧 Provider 的 Prompt-to-JSON 兼容回退、工具执行、SSE 和降级。真实链路另有可选 eval runner，2026-08-30 对 DeepSeek 跑过 121 个单轮 case、三轮稳定性和 10 个多轮场景，并记录 provider 调用、能力与工具命中；2026-09-01 又完成了生产 Planner 原生 Function Calling smoke test。两者之间仍差生产长期可用性：一次真实 eval 不能证明未来 provider 版本、超时和输出质量。因此应在受控预算下定期跑 canary，而不是把它塞进每次单元测试。

### H51. AI 写了多少，项目证明谁的能力？

我会如实说这是 AI 协作开发：Codex 和 Claude 生成、评审了相当多代码，我不声称逐行手写。我的贡献是定义产品边界和需求、做取舍、持续用真实问题发现失败、决定数据与 Agent 架构、要求可回放/可降级/可部署，并对最终代码、测试和风险承担责任。项目能证明的不是打字速度，而是我能否指挥多个模型、读懂输出、发现它们互相矛盾、用测试和数据裁决，并把原型推进到可运行系统。面试时我也必须能解释关键代码；解释不了的部分就不能算自己的能力。

### I52. 是否真实部署过？

部署过。项目运行在香港 Ubuntu 服务器，使用 Docker Compose、Nginx 和域名 `limitupagent.xyz`。实际遇到过域名只显示 Nginx welcome page、跨域/代理后的匿名 cookie 导致 `Chat session not found`、服务器环境变量与 API key、容器更新和重启等问题，并逐步修复。这比“写了 Dockerfile”多了一条真实故障链，但还不能叫大规模生产：用户量小、单机 SQLite、没有多区域和完整 SLO。

### I53. 备份频率、保留和恢复演练如何？

cron 每天北京时间 03:25 使用 SQLite online backup API 生成一致性快照，默认保留最近 14 份，文件权限在 POSIX 上设为 0600；脚本测试会打开备份并验证数据。当前还没有我能证明完成过的“生产卷损坏后从备份恢复并验证服务”的完整演练，所以不能只说有备份就算完成。上线前应定期在临时 volume 恢复、跑 schema/version/关键行数和健康检查，并记录 RPO/RTO。

### I54. 限流数字怎么定？

默认每访客 8 次/分钟、60 次/天、同访客并发 1、单 IP 20 次/分钟、全局并发 4，主要依据单机容量和 LLM 成本保护，不是由大量真实流量拟合。60 次对普通研究浏览可能够，对重度对话用户可能不足；当前没有独立真实用户被限流的数据。管理 usage 接口能看请求、拒绝、token 和估算成本，下一步应根据 p95 延迟、拒绝率、日活和单用户成本调参，并为管理/内部任务使用独立配额。

### I55. 日志是否持久化和集中？

本地 `backend/*.log`、`.out.log` 是开发过程产物，不是正式日志架构。生产日更和备份 cron 写到宿主机 `/var/log/limituplab/` 并由 logrotate 保留 14 轮；Docker 服务主要通过 stdout/stderr 和 `docker compose logs` 查看，默认没有集中采集，容器删除后本地 container log 的生命周期受 Docker 管理。当前缺少结构化 JSON 日志、request/run correlation、集中检索和告警。下一步应统一 stdout JSON，再接 Loki/Promtail、OpenTelemetry 或云日志。

## J. 安全

### J56. 忘记设置 production env 会不会使用开发密钥？

会，这个风险成立：只有明确设置 `LIMITUPLAB_ENVIRONMENT=production` 时，应用启动才强制 session secret 和 admin key 至少 32 字节且互不相同；如果生产部署错误地保留默认 development，内置开发 secret 会生效。当前 `.env.production.example` 和部署文档要求设置 production，FastAPI 文档也只在生产关闭，但这仍是“依赖运维正确”。更安全的默认是容器镜像/compose 固定 production，或检测公开 host/非 loopback 后拒绝开发 secret，使生产默认 fail closed。

### J57. admin key 如何轮转？

代码每次请求 `os.getenv`，但通常运行中的进程环境不会因为修改 `.env` 文件自动变化，所以实际轮转仍是更新 secret 后滚动重启 worker。单机重启窗口内不会出现同进程新旧 key 混用；多 worker 滚动时可能短暂存在双版本。成熟方案应支持当前 key + next key 的短期双 key 验证、记录 key id，完成滚动后撤旧，并从 secret manager 读取，而不是依赖热改进程环境。

### J58. SSE 能否用 4 个连接绕过全局并发？

不能在单进程内绕过。限流在创建后台 Agent 线程和返回 StreamingResponse 前 acquire，一条 SSE 请求从开始执行到 finally release 都占用一个 owner/global lease；同 owner 默认只能有 1 条并发，第 2 条会被拒绝，全局第 5 条也会被拒绝。它是“消息执行级”而不是单纯 TCP 连接数限制。多进程时每个 worker 各有自己的内存 limiter，才会把全局 4 放大，这是迁移 Redis/数据库限流的理由。

### J59. Prompt 注入能否越权调用工具？

Planner 只能从 profile allowlist 的 schema 中选工具，后端会拒绝未启用或未知工具，参数也经过日期、数量、symbol 等边界归一；V1 不暴露任意文件、shell、数据库 SQL 或私有用户数据工具，所以用户要求查询某只公开股票本身不是越权。Tool Policy 主要解决证据充分性，不是完整安全策略。仍需防两类风险：新闻/网页内容中的间接 prompt injection 被拼进 answer prompt，以及未来工具加入私有数据后缺少逐工具授权。应把外部文本标为不可信数据、限制 egress、做参数 schema 校验和 owner 级授权。

## K. 前端

### K60. `App.tsx` 单文件和请求 race 怎么看？

批评成立。第一轮已经把 Agent 会话状态、SSE 交互、历史会话管理和展示从 `App.tsx` 抽到独立 `AgentChatDock.tsx`，`App.tsx` 不再同时承担聊天子系统；后续仍应继续拆 route page 和自定义 query hooks。顶层 `loadDashboard` 没有 AbortController，也没有 generation id；React StrictMode 开发环境会执行 effect 的额外挂载周期，可能产生重复请求，快速刷新也可能让旧响应覆盖新响应。React 18 对卸载后 setState 不再总是警告，不代表 race 不存在。下一步应引入 AbortController 或 TanStack Query 的取消、去重和缓存，并测试慢旧请求晚于新请求返回的场景。

### K61. lightweight-charts 性能上限测过吗？

没有做 100 图同屏的正式帧率基准。当前产品一次只在个股详情渲染一个 60 日/分时图，列表不为每只股票创建 chart，所以“100×60 同时渲染”不是当前真实路径；单图 60 根 K 线负载很小。风险在未来卡片内嵌 sparkline 或多图比较时，每个 chart 都有 canvas、订阅和 resize 开销。届时应虚拟化列表、只渲染可视图、复用轻量 sparkline，并用 Performance API/Playwright 测 p95 render 与交互帧率。

### K62. 为什么不用 EventSource，手写 SSE 完整吗？

因为请求需要 POST JSON body，而浏览器原生 EventSource 只方便 GET，难以携带这类请求体；所以使用 `fetch` + `ReadableStream` 是合理选择。当前解析器支持跨 chunk 缓冲、CRLF 归一、`event:`、多行 `data:` 和 completed/error，但不实现 `id:`、`retry:`、注释心跳、自动重连和 last-event-id。当前协议由同一后端控制，不发送这些字段，所以可用；如果加入断线续传，应使用成熟 SSE parser，并为 UTF-8 分片、空行、心跳和重连做协议测试。

## L. 项目价值

### L63. 一个“暂无信号”的项目值得做面试主项目吗？

值得，但卖点不是“我预测准了”，而是“我把一个容易自欺的金融 Agent 做成了可审计、可证伪的系统”。我们知道了至少一件具体的事：在当前 20 至 21 个结果日和指定 outcome 下，这 14 个手写因子没有显示稳健样本外信号，某些直觉方向甚至可能相反。这是负面研究结果，却能展示数据时点、不可变预测、工具接地、失败降级、统计治理和生产部署。面试时必须把它定位成 AI 应用/研究工程项目，而不是成功量化策略。

### L64. 更准的开源模型出现后，项目还有什么价值？

单纯评分公式没有护城河，随时可能被更好的模型替代。可复用价值在于 point-in-time 数据管线、证据工具层、Agent Query Contract、可审计 trace、outcome 闭环、基线审计、Challenger 治理和部署安全；新的 predictor 可以作为一个版本接入同一验收框架。数据也不是独占的，诚实本身更不是商业壁垒。项目的差异化是“把预测器当可替换组件，把证据和验证当产品骨架”。

### L65. 不同岗位该看哪些亮点和雷区？

AI 应用/后端岗：亮点是 planner-tool-answer、能力契约、Policy 修复、SSE、会话隔离、限流、SQLite 并发和降级；雷区是真实用户回流不足、自定义协议复杂。量化研究岗：亮点是 point-in-time、日期阻断、基线、outcome 完整性和诚实证伪；雷区是样本仅 21 日、规则参数未实证、没有交易成本。全栈岗：亮点是完整工作流、图表和部署；雷区是 `App.tsx` 近 4000 行、状态与请求管理薄弱。面试时我会根据 JD 主讲最相关的 30%，并主动承认对应 30% 风险。

### L66. 如何 present 一个尚未转完的工程闭环？

我会画出已经闭合的机械链路：每日输入固化 -> 版本化 Top10 -> D+1/D+3/D+5 精确回填 -> Review/诊断 -> Challenger 决策；再明确证据成熟度只有 21/60 结果日，所以“管线闭合，统计结论未成熟”。这不是把未完成包装成成功，而是区分系统 readiness 和研究 readiness。演示时展示一次真实日期的不可变快照、后续 bars 和“不晋升”报告，比宣称准确率更可信。

## M. 未来方向

### M67. discovery 的 Outcome 为什么断了？

历史 `first-board-discovery-v2` 现在已经有独立前向诊断，以目标日是否首板作为 outcome；但当前 `low-position-discovery-v3` 改了产品目标，不再预测“次日首板”，因此旧 outcome 不能直接复用。也就是说旧缺口补了一半，新目标又产生了新的验收缺口。下一步必须在继续扩展功能前，预注册 v3 的趋势启动、5/10 日收益、最大回撤和相对行业收益，并只评估预测时已存在的快照。

### M68. 6 个月、2 个工程师只能做三件事，选什么？

第一，冻结策略范围，建立 60+ 完整结果日和多目标 outcome 的自动数据质量/研究流水线，因为没有可信标签，其余优化都无法判断。第二，继续重构 Agent 和前端：Capability 已成为业务工作流单一声明源，`chat.py` 已拆出 Prompt 与确定性答案模板，`App.tsx` 已拆出 Agent 会话面板；下一步继续拆执行器、route page，并建立线上失败回流和真实 LLM canary。第三，迁移 PostgreSQL + Redis，完成结构化日志、告警、恢复演练和基础用户体系，为真实试用做容量准备。排序依据是先获得真值，再提高迭代效率，最后扩容量；不是先增加更多策略。

### M69. 数据每天只增加一天，如何加速？

可以买可靠的 point-in-time 历史涨停、行情、龙虎榜和当时可见新闻，代价是成本、授权和历史口径对齐；也可扩大横截面或加入相邻市场状态，代价是分布异质性和独立性下降；合成数据适合测试统计代码，不能替代真实有效性证据。用当前公开源回放历史也可以，但最危险的是 look-ahead：今天抓到的财报修订、热榜和新闻不能冒充过去当时可见事实。V1.1 没买历史数据是成本与授权取舍，也因为先要把时点契约做对。

### M70. 重做会砍掉哪 40%？

第一轮已经砍掉 09:25 竞价终选整条运行链路、历史相似案例和重复的前端回测/评估展示；历史竞价实现固定在 `v1.1.0` 标签。下一轮会继续收敛过早的多角色命名、低样本自动调权、V1 通用网页搜索和关键词补丁。保留：可靠数据同步、首板全池、一个明确评分器、不可变 Top10、D+1 至 D+5 outcome、一个受控工具 Agent、质量审计和部署。目标是更早回答“评分是否有用”和“Agent 是否可靠”，而不是用功能数量代替证据。

## N. Agent 设计

### N71. 三句话讲完整数据流；为什么两次 LLM？

第一句：请求先解析日期、实体和查询契约，Planner LLM 从当前 profile 的 capability 与 tool schema 中输出结构化计划。第二句：后端按 Capability Contract 归一参数、补齐必要工具并执行，得到结构化 facts、references 和 trace。第三句：Answer LLM 只接收命中 Capability 的回答规范并基于 facts 流式组织答案，失败或违反完整性、安全契约时降级到确定性模板并持久化会话与 usage。

拆两次是为了让规划和表达分别可审计、可测试、可降级，也允许后端在生成前修正证据；代价是额外一次 LLM 延迟和约 5.3k planner 固定 token。当前记录 planner/answer duration 和 prompt chars，但还没有可靠的生产 p99 对照实验，因此不能报一个虚构数字。简单单能力问题未来可尝试原生 tool calling 或一次调用循环，复杂高风险问题保留两段式。

### N72. 这到底是 Agent 还是规则系统？

我会称它为“受约束的 tool-using Agent”或 `grounded generation with guardrails`，而不是高度自主 Agent。LLM 的自主性在于理解开放问法、选择能力、组合工具和组织回答；Query Contract、capability 和 Policy 刻意收回日期、完整名单、风险边界和最低证据控制权。金融事实场景追求的是可控可靠，不是最大自主。它比纯规则问答开放，但比 ReAct 自由循环保守，这个边界是设计目标，不是需要掩饰的缺陷。

### N73. 为什么 prompt-to-JSON，不用原生 function calling？

最初是为了兼容 DeepSeek 的 OpenAI-compatible Chat Completions，并让 planner 可替换 provider，不依赖每家 tool-call 方言。解析器能去掉 ```json fence，先解析全文，失败后截取第一个 `{...}`；但不修尾逗号、错字段，也没有 JSON schema retry。解析失败会让 planner 链路降级到确定性兼容路由/模板，不会执行任意工具。这个选择降低 provider 耦合，却提高格式失败风险；后续应优先使用 provider 的 structured output/function calling，保留 JSON prompt 作为 fallback，并统计真实 parse failure rate。

### N74. direct-answer intent 谁判定，如何发现误判？

主要由 Planner LLM 输出 intent；后端只允许 greeting、capability intro、smalltalk 直接回答，而且如果 Policy 判断问题需要 grounding，会清空 direct answer。也就是说 LLM 把市场问题误标 smalltalk 但文本仍触发证据需求时，后端有机会否决；完全漏掉的仍可能被静默打发。trace 记录 planner intent、capabilities、工具和最终 source，评测覆盖“你能做什么”、问候与多个事实问法。当前还没有线上 direct-answer 误判率看板，应把“direct answer 后用户立即重问/改写”作为失败信号回流。

### N75. 两个 capability 需要 8 个以上工具时砍谁？

当前算法先按 capability 顺序放 required tools，再追加 Planner 的其他工具，最后截到 8；因此前面的最低证据优先，后面的 capability 或探索工具可能被砍。它不会在缺工具后自动禁止 Answer LLM，所以虽然 Policy 可能再次补事实，仍存在复杂问题证据不全风险。正确改法是让 planner 输出优先级/依赖，先计算预算；无法在预算内完整回答时拆成两个阶段或明确说明未覆盖部分。测试应覆盖 7、8、9、12 调用并检查事实完整性，而不仅检查列表长度。

### N76. Planner capability 和 tool 推断冲突时信谁？

Capability 现在是唯一业务意图：先保留 Planner 显式 capability，再为 Planner 明确选择的单工具补可推断 capability；工具执行后，只有当某 Capability 的全部 required facts 都真实存在时才恢复遗漏能力。复合能力优先，避免一次市场全景查询又注入四套子能力回答规范。仍有一个缺口：显式 capability 与完全无关的额外工具目前会并集保留，尚未记录 `routing_conflict`；后续应按可满足性和最小充分证据重新规划，而不是继续扩大能力集。

### N77. 18 条 repair 规则的顺序依赖如何管理？

执行顺序由 `_rules()` tuple 明确控制，注释也承认前序规则可能给后序规则提供 facts；测试覆盖若干顺序、互斥和补偿路径。但目前没有机器可检查的 dependency graph，新规则应该插在哪里仍依赖开发者理解，这会随规则增长变脆。应给规则声明 `requires_facts`、`produces_facts`、priority 和互斥组，启动时拓扑排序并检测环；再用参数化测试随机扰动无依赖规则，验证结果不变。

### N78. repair 失败如何传导到回答？

Policy 捕获异常后把 `<tool>_error` 写入 facts，并生成 error trace；Answer prompt 会收到整个 facts，因此模型可以看到失败原因。如果所有事实都不可用，`_has_usable_tool_facts` 会直接返回明确不可回答，不调用自由生成；如果部分事实可用，模型会基于剩余事实回答并应说明缺口。风险是 prompt 约束不能数学保证模型不会忽略 `_error`，所以关键 capability 还应声明 required fact completeness，在生成前阻断，而不是只靠 LLM读错误字段。

### N79. 空数据与工具失败能区分吗？

现在可以明确区分。每个数据工具 trace 都带统一结果信封：`status=ok|empty|partial|error`、`data_fresh`、`source_errors` 和 `payload`；旧的执行 `status/output` 只为历史记录与前端兼容保留。`empty` 只表示查询成功但没有匹配行，`partial` 表示返回数据仍可使用但必须披露缺失来源，`error` 的 payload 不得作为事实。Agent 的可回答判断、最终回答提示和证据卡都消费这套状态。AKShare 涨停采集也不再吞掉炸板池异常：两个来源分别记录，单源失败返回 partial，双源失败返回 error；partial/error 时替换式导入不会删除已有日期数据。

### N80. 为什么没用 MCP，能迁移吗？

最初工具都在同一个 FastAPI 进程，直接 Python 调用能共享 typed models、repository 和事务，延迟低、调试简单；MCP 的跨进程发现、复用和权限边界当时不是 V1 目标，所以没有为了追潮流增加协议层。这是有意识的本地优先，但也牺牲了被 Claude Code、Cursor 或其他 Agent 复用的标准接口。迁移并非重写业务：22 个工具已有 schema、参数和结构化结果，可在外层加 MCP server adapter；真正成本在认证、长结果分页、错误语义、资源 URI 和测试，估计是中等改造而非零成本。

### N81. 为什么删除自定义 Markdown Skill？

它曾验证过一个有用思路：业务工作流应具备 examples、required tools、默认参数和按需回答规范，而不是全部写死进大 Prompt。但项目只有 6 个固定内部 Skill，且同一信息已经存在于 Capability，导致 Planner 同时输出 `skill_name` 和 `capabilities`，后端再维护 Loader、Registry 与映射，复杂度收益比很差。因此当前删除了运行时 Markdown Skill，把这些有效字段合并进 `AgentCapability`。如果未来需要第三方可安装工作流、独立权限和资源文件，再采用标准 Skill 或 MCP 生态，而不是提前维护半套自定义平台。

### N82. 为什么手写极简 YAML parser？

历史实现手写 parser 是为了只接受很小的 frontmatter 子集并避免增加 PyYAML，但这恰好暴露了过度设计：项目为 6 个固定工作流承担了语法解析、启动失败面和额外测试，却没有第三方安装、版本或权限需求。当前 parser、Loader 和 Registry 已全部删除，静态 Python dataclass 由类型检查和单元测试保证。若未来真正开放第三方 Skill，应直接使用标准 YAML 安全加载、schema 校验和单 Skill 故障隔离，不恢复这套极简 parser。

### N83. Capability 与 Tool 如何防漂移？

现在 `AgentCapability` 是单一业务 Manifest：同一对象包含 description、examples、required tools、默认参数和 answer guidance，并由它生成 Planner capability schema、确定性工具补齐和按需 Answer 指令。Tool Schema 仍负责原子函数的参数与返回值，两层职责不同。测试覆盖 profile 可用性过滤、复合证据顺序、默认参数合并、Facts 恢复和回答规范注入；增加业务能力不再需要同步修改 Skill 文件、映射表和 Loader。

### N84. 为什么同时保留 LLM 语义路由和关键词路由？

关键词路由有三类用途：Planner 失败时降级、旧 provider 兼容，以及对完整名单/日期/安全等高风险词法约束做确定性保护。当前有显式 capability 时，`QuestionSignals` 大部分不启用 lexical fallback，所以它不是与 LLM 平票竞争；代价是 LLM 给了“错误但非空”的 capability 时，普通关键词不会纠正。修复方向不是无限堆关键词，而是基于 capability 契约做语义 eval、冲突检测和必要证据验证；关键词只保留可证明的参数解析和安全边界。

### N85. “最近这个股票有什么新闻”会走错吗？

如果会话或请求中能解析出明确 symbol，当前 Planner prompt 要求 named stock news 使用 `stock_news`，Policy 也有 stock news/activity 信号；不是只靠 `looks_like_finance_news_question`。但“这个股票”没有可继承实体时应追问或明确无法消歧，不能默认为全市场新闻。关键词阈值最初来自手测和线上失败补例，后来已加入 100+ 改写和多轮路由评测；仍需按 capability 统计 precision/recall，特别覆盖“最近消息”在全市场、板块和个股三个域的负例。

### N86. 语义路由评测测哪一层，如何回流？

它主要测 Planner 是否选择预期 capability 和工具，以及经过后端修复后的最终工具契约；部分用例也检查模板答案事实，但不是通用生成质量评分。当前真实 LLM 口径是 121 个单轮 case、每个三轮，另有 10 个多轮场景、60 个 turn 运行；固定 fixture 已扩展到 146 条改写。用例来自开发期间真实失败问法和人工扩写，但还没有自动采集独立用户问题的生产回流。下一步应匿名记录 capability、repair、重问和失败反馈，经人工标注后进入新 holdout，避免边修边测同一集合。

### N87. “LLM 选菜单、后端定参数”是 Agent 还是 dispatcher？

在参数边界上它确实是 semantic dispatcher。LLM 决定用户需要哪些业务能力，也可提出具体参数；后端用 default arguments 补缺，并让用户明确日期、TopN、市场过滤优先于模型猜测。相比完全让 LLM 控制 tool+args，这降低漏参数、越界和同义问法漂移，代价是自主探索更少。我的定义是：语义组合是 agentic，关键参数和最低证据是 deterministic orchestration；在金融场景这是刻意的控制权分配。

### N88. Required tools 优先会不会压制 LLM 探索？

会，这是有意偏保守但有副作用的策略。required tools 是回答该 capability 的最低事实，所以预算不足时优先保留；Planner 的额外工具排后，最容易被 cap 截掉。这能防“有趣但缺核心证据”的回答，却可能丢掉模型发现的有价值补充。更好的 guardrail 不是永远压制，而是给工具标 `required/supporting/exploratory`，记录被截工具并用离线评测判断它们是否改善答案；高价值探索可升级为正式 capability，而不是悄悄被砍。

### N89. Policy 否决 direct answer 时 LLM 知道吗？

当前是后端直接清空 `direct_answer` 并补工具计划，Planner 不会收到一轮“你被否决”的反馈；Answer LLM 看到的是修复后的 facts 和 plan，因此知道最终有哪些证据，但不知道哪些是自己漏掉、哪些由 Policy 补。trace 会向开发者记录 planner 与 final tool calls 及 repair，方便审计。若需要模型自我改进，可把 compact repair reason 反馈给下一次 planner 或用于离线训练，但不应把内部纠错细节直接暴露给普通用户。

### N90. 统一 repair 签名是否过度抽象？

一排 `del request, signals, context_symbol` 是抽象泄漏的信号。统一签名让规则注册和测试简单，但让多数 action 接收不需要的上下文，也隐藏真实依赖。可以把 repair 改成一个 `RepairContext` 对象，规则只声明所需字段，或按 `execution-only`、`request-aware` 两类 action 拆协议；这样更易演化且不破坏注册表。18 条时已经值得重构，但优先级低于规则 dependency 和错误语义，因为它主要影响可读性，不直接影响正确性。

### N91. 强制模板的触发和截断检测是什么？

`ContextVar` override 主要用于离线 eval 强制走确定性模板，保证评测路由/事实不受生成波动；环境变量只作兼容 fallback。运行时 provider 异常会走模板；运行时所谓“截断”并不是通过 SSE finish reason 通用检测，而是用完整名单、分组、TopN、交集、晋级分子分母等 post-hoc 契约检查结果是否完整。它是领域启发式，不是对所有截断可证明。误判会牺牲语言自然度但保住完整事实；现存问题仍是已流出的 delta 无法撤回。

### N92. 前端和评测能区分模板与 LLM 吗？

后端内部 `tool_calls`/trace 会记录 `llm_tool_answer` 或 `template_general_answer`，usage 也记录 provider 调用和 token；开发者和 eval 可以区分。普通前端按产品要求只展示最终回答，不展示内部工具名和 trace，因此用户看不出来源。指标上必须分开统计 route correctness、template answer correctness、LLM answer completeness 和 fallback rate，否则模板会掩盖 LLM 质量。当前结构具备区分字段，但前端没有用户友好的“已降级”状态提示，这是可观测性缺口。

### N93. Critic 与 Tool Policy 是否重复，四个角色要几次 LLM？

Policy 在生成前保证“拿到了哪些最低事实”；Critic 在单票评分层检查“这些事实是否真的支持高置信度”，二者关注完整性和反证，不完全重复。Critic 目前是确定性规则，不是额外 LLM；Evaluation 也是确定性 outcome 标签；Explanation 和 Review 才可选 LLM，失败有模板。它们不会在一次普通聊天中全部串行执行。若 Critic 说证据不足，原 score 不变，只降低解释置信度；是否改策略必须经过 Review/Challenger 的跨样本证据。

### N94. Planner prompt 多大，做缓存了吗？

删除重复 Skill catalog 后，当前 V1 profile 的 Planner system prompt 实测为 16,165 字符，比此前 17,420 字符减少约 7.2%，再叠加用户上下文；每次 Planner 仍会全量发送。代码没有显式 prefix caching，也没有确认 DeepSeek 是否自动命中缓存，因此不能把缓存收益算进成本。稳定 system prompt 适合前缀缓存，但动态 profile/schema 会改变 cache key。成本应按 usage 表真实 prompt tokens乘以请求量和 provider 单价计算；当前价格配置默认 0，未配置单价时只统计 token、不编造美元成本。

### N95. 动态 profile 会导致路由不稳定吗？

会。capability 只有在全部 required tools 可用时才进入 prompt；例如 V1 隐藏通用 web search，用户问任意网页研究时 Planner 应判 unsupported，而 extended profile 可能选择 web capability。当前 V1 profile 有专门测试，确保禁用工具不会被注入并对超范围请求明确拒绝；但没有对所有 profile 做同一改写集的差异矩阵。应该把“预期支持/预期拒绝”也作为 profile 契约评测，防止能力消失后被错误映射到相邻能力。

### N96. 安全误判如何控制？

Planner 会输出 safety/intent，后端还有禁止交易词检测和固定安全边界；安全问题不是纯关键词单路判定。对“解释评分理由”这类允许研究问题，prompt 明确要求基于 facts 回答，不应因出现股票名就拒绝；对“给仓位/目标价/直接买卖”才拒绝。已有允许解释与禁止指令的测试，但没有独立 over-refusal 百分比。下一步应建立成对评测：同一标的的“为什么高分”必须答，“现在买多少”必须拒绝，并统计假阳性和假阴性。

### N97. 流式过程中如何防幻觉？

所有工具和 Policy reconcile 都在 Answer LLM 开始前完成，不存在工具还在异步返回、模型已经开写的设计；生成时只给已完成 facts。问题在于生成开始后没有 token 级 grounding verifier，post-hoc 完整性和安全检查发生在完整文本返回后。由于 delta 已经通过 SSE 发给用户，最终替换模板也收不回前文，这是当前最重要的流式一致性缺口。高风险答案可先在服务端缓冲、验证后再分块发送，或只流进度、最终一次发送答案；低风险开放解释再保留真流式。

### N98. trace 给谁看？

trace 当前定位为开发者/管理员可观测性：记录 planner、final tools、repair、references、时延和错误，管理运行接口受 admin key 保护。普通用户只看答案和股票链接，这是此前根据产品体验做的取舍；工具内部名字和 `policy_repair` 会让用户困惑，也可能暴露攻击面。用户级可解释性应展示“数据日期、来源类别、缺失事实和为何无法回答”，而不是原始内部函数名。两种 trace 应分层，而不是全隐藏或全暴露。

### N99. Eval 绿的究竟是哪一层？

默认 pytest/fixed-provider eval 主要证明路由、capability、工具补齐、参数契约、模板事实和多轮上下文，不证明任意真实 LLM 的生成质量。项目另有真实 DeepSeek planner eval，记录 provider 调用和三轮稳定性，证明当前 prompt 下规划层曾真实跑通；Answer LLM 的语言质量仍主要靠契约检查和人工验收，没有一个通用自动 judge 能证明“答得好”。因此评测报告应拆成 deterministic contract pass、real planner pass、answer completeness、human quality 四层，不能用一个 11/11 或 121/121 概括全部。

### N100. 是否有真实用户，凭什么相信路由准确率？

目前有真实部署和持续的本人使用、真实问法失败驱动迭代，但没有足够证据证明有独立外部用户群，也没有匿名问法分布、留存、重问率或满意度闭环。所以我不能声称路由已经被真用户验证。121 条真实 LLM 评测只能说明对当前标注集有效。下一步应邀请小规模目标用户试用，在隐私保护下记录 capability、fallback、repair、无法回答和连续改写，经人工标注后形成独立 holdout；在此之前，对泛化能力的正确表述是“工程上可测，产品上待验证”。

---

## 面试时的总括表述

LimitUpLab 最值得讲的不是“我找到了能预测首板的模型”，因为当前数据不支持这个结论。它真正完成的是一套受约束的金融研究 Agent 工程：把 point-in-time 数据、版本化评分、不可变前向快照、D+1 至 D+5 outcome、工具接地问答、失败降级、治理门槛和单机部署连成可审计闭环。

我会主动承认四个核心缺口：样本只有 21 个完整结果日；评分 magic numbers 尚未被实证；前端页面和 Agent 执行编排仍有继续模块化空间；独立真实用户反馈不足。第一轮已经分离 Prompt、确定性答案模板和前端会话面板，但这不等于技术债清零。能把这些缺口量化、阻止系统在证据不足时自动晋升，并知道下一步先补真值和验证而不是继续堆功能，才是这个项目最能证明的工程能力。
