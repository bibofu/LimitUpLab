## 2. 已落地的架构与配置

```text
API 实例 / 采集任务 / 质量评估 worker
                │
    app.database.connect / begin_write
                │
        ┌───────┴──────────┐
  SQLite 兼容路径     PostgreSQL 传输适配
  原数据库文件        SQLAlchemy 连接池 + psycopg 3
                           │
                      PostgreSQL 18
                 Alembic + 共享状态 + 审计记录
```

- 配置 `LIMITUPLAB_DATABASE_URL` 时使用 PostgreSQL；未配置时保留 SQLite 路径。显式指定 SQLite 文件的调用仍可用于本地测试、备份和离线核查。
- PostgreSQL 入口位于 `backend/app/storage/`，没有新增原计划中的 `app/db/` API，也没有引入 ORM 全量重写。
- SQLAlchemy 负责连接池、Schema metadata 和迁移/导入工具；既有 Repository 保留显式 SQL，psycopg 3 负责实际数据库传输。没有引入 `psycopg_pool`。
- 每进程默认连接池为 `LIMITUPLAB_DB_POOL_SIZE=5`、`LIMITUPLAB_DB_MAX_OVERFLOW=5`，可设置池等待超时。增加副本前，应把全部 API、采集和评估进程纳入总连接数预算。
- `/ready` 检查数据库和 Schema 就绪状态。PostgreSQL 未迁移或版本不符时拒绝就绪，业务请求不会自动修改结构。
- 默认 Compose 与 SQLite 发布脚本继续有效。PostgreSQL 使用 `docker-compose.postgresql.yml` overlay 和独立数据卷，保留原 `limituplab-data` 卷。
- PostgreSQL 服务、备份客户端和 CI 统一为 18。官方 18 镜像的持久卷挂载到 `/var/lib/postgresql`，数据库数据位于其版本子目录。

## 3. 数据语义与 Schema

当前 Alembic head 为 `0003_single_champion`：

| 版本 | 内容 |
| --- | --- |
| `0001_postgresql_baseline` | 冻结 SQLite v12 及最终 ReAct/质量评估结构，共 41 张业务表；外键、唯一约束、索引和不可变审计触发器 |
| `0002_runtime_coordination` | `runtime_leases`、`agent_request_attempts`、`agent_request_slots`、`agent_request_days` 四张协调表 |
| `0003_single_champion` | Champion 策略部分唯一索引，防止同时存在多个 Champion |

`app/storage/schema_v0001.json` 是固定历史基线。后续结构变化应增加 Alembic 版本，不能重新生成 baseline 来修改已经发布的历史版本。

| SQLite 数据 | 本期 PostgreSQL 表达 | 保留目的 |
| --- | --- | --- |
| JSON 原文 | `TEXT` | 保留空白、键顺序、数值文本与历史内容哈希，不重新序列化历史证据 |
| 交易日、创建时间等文本 | `TEXT` | 不在换库时同时改变业务日期、时区或序列化约定 |
| `REAL` | `double precision` | 保持已有浮点计算语义 |
| `INTEGER`，包括 0/1 标记 | `bigint` | 保持既有整数契约；未改为 boolean |
| 原自增整数主键 | Identity | 导入显式旧值，导入后校准序列 |
| 消息和工具调用 `rowid` 顺序 | `legacy_order` Identity | `chat_messages`、`react_calls` 导入原 rowid，新记录继续生成顺序号 |

涉及时间比较、冲突处理、错误分类和返回行行为的差异在明确的适配位置处理。`?` 参数绑定使用词法扫描适配，不做全局正则替换 SQL，也不执行 SQLite 专属 DDL。

质量审核、证据包和终结评估记录继续受不可变触发器保护。预测来源、历史快照与内容哈希保留，不能把历史回测结果改写成 live 记录。源库存在多个 Champion 时，导入明确失败，不能自动选择或删除其中一个。

## 4. 并发与多实例基础的实际边界

| 能力 | 已实现 | 尚需验收或后续工作 |
| --- | --- | --- |
| 写事务一致性 | PostgreSQL 写入使用事务级全局 advisory lock，保持原读改写顺序 | 未拆成按业务键/记录锁；未证明并行写吞吐提升 |
| ReAct 执行归属 | 数据库租约、数据库时钟、所有权令牌与 fencing；旧执行者失去租约后不能继续发布 | 真实多容器故障、网络中断和负载均衡行为仍需部署验收 |
| 恢复 | 检查点及工具记录持久化，重新提交同一请求可按已有记录恢复 | 没有交付通用后台自动接管调度器；外部调用未落库时的不确定结果仍需按工具幂等能力处理 |
| SSE | 从持久化事件和运行状态续读，本地通知仅作为唤醒优化 | 生产代理重连、超时及跨实例分流验收；未引入 LISTEN/NOTIFY 或 Redis 事件总线 |
| 取消 | 取消状态持久化，其他实例的执行控制可感知 | 生产环境下长时外部调用的取消延迟需测量 |
| 限流与并发额度 | 请求尝试、日额度、并发槽位共享存储，避免额度随副本数放大 | 连接池和热点写锁压力待负载测试 |
| 后台唯一任务 | 日更与推荐刷新使用共享租约，写入校验执行所有权 | 真实调度器重启、重复触发与长任务失联验收 |
| 最新新闻 | PostgreSQL 模式使用共享数据库快照，并拒绝旧结果覆盖新结果 | 其他进程内采集缓存未统一改为分布式缓存 |
| 本地文件 | 原 SQLite、备份和运维产物继续保留 | 未把所有报告和备份搬到对象存储；跨主机产物分发需独立安排 |

独立进程租约排他、租约失效后的写入保护、共享额度、并发策略发布等已有自动化测试。它们覆盖实现契约，不等于“多个生产 API 副本、代理和后台任务整体运行已验收”。

## 5. 导入与恢复：已完成的全量演练

2026-10-19 使用 SQLite backup API 从本地原库创建一致性副本，整个导入只读该副本。目标为独立 PostgreSQL 演练库，没有改变默认应用连接。

| 项目 | 实测结果 |
| --- | --- |
| SQLite 一致性副本大小 | 273,821,696 字节 |
| 已导入数据 | 41 张既有业务表，共 691,526 行 |
| 新协调表 | 4 张，初始为空 |
| 数据核对 | 导入前后逐表行数及有序全字段 SHA-256 一致 |
| 源副本保留 | 导入前后文件 SHA-256 不变 |
| 遗留表 | 5 张，共 6 行，仅保留在 SQLite，导入报告包含结构和校验值 |
| 导入时间 | 本地演练约 28.9 秒，仅代表该数据集与机器 |
| 备份恢复 | 自定义格式备份恢复到另一独立空库，45 张表、691,526 行再次完整核对一致 |

遗留表为 `auction_final_recommendation_snapshots`、`auth_challenges`、`auth_sessions`、`user_identities`、`users`。导入必须逐一显式确认保留，遇到未确认遗留表或未知列差异会停止；原 SQLite 不会被删除。

导入程序 `backend/scripts/migrate_sqlite_to_postgres.py` 采用 SQLAlchemy 分批插入，**没有使用 COPY**。目标必须为空；导入期间锁住目标表，所有插入与核对放在同一事务中，失败整体回滚。成功后校准 Identity 序列。再次对已导入目标执行会拒绝，不会清空重导。

本地证据保存在忽略提交的 `output/pg-migration-report.json`、`output/pg-restore-verification.json` 和备份文件中。正式切换需要使用生产当时的新快照重新执行，不能直接复用本次演练报告。

## 8. 后续切换步骤与回退边界

1. 按 [部署手册](../deploy/postgresql.md) 在实际环境准备 PostgreSQL、独立备份位置、应用配置和共享密钥；先验证镜像与 Compose。
2. 完成单实例功能演练，明确连接预算与停写窗口；两个实例的并发/故障验收是后续扩容的独立门槛。
3. 停止所有写入口、日更、刷新和评估任务；排空或保存运行状态，再创建生产 SQLite 一致性备份。
4. 对空 PostgreSQL 目标执行 Alembic、只读导入和完整核对。保留原 SQLite、备份和核对报告。
5. 启动单实例，通过就绪检查、业务读取、实际 Agent 问答和恢复验证后，再恢复写流量与后台任务。
6. 观察错误率、队列与锁等待、池耗尽和 SSE 行为，再决定生产扩容。

**PostgreSQL 开始接收新写入之前**，可以恢复旧代码与冻结的 SQLite。**开始接收新写入之后**，旧 SQLite 已经落后，不能只改连接配置回退，也不允许把丢失新会话或审计记录视为默认可接受。需要先停写、核对并同步新增数据，或从 PostgreSQL 备份恢复到新库。

本期不安排删除 SQLite 兼容层、原备份脚本、WAL 配置或原数据卷。是否移除 SQLite 需要后续明确决策，不能作为本次迁移的自动清理步骤。
