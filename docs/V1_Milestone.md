## 1. 里程碑说明

`v1.0.0` 标记了 LimitUpLab 首个可用、可部署的阶段基线。此后 V1 继续围绕“完整收盘数据 + 首板一进二研究”做范围收敛和质量验收，不再把新增功能数量当作完成标准。

V1 的最终产品边界是：在交易日收盘后生成首板质量评级和次日一进二 Top10 观察候选，并用 D+1 至 D+5 真实结果持续复盘。盘中行情、集合竞价、实时热榜、实时板块、实时新闻和其他交易策略延后到 V2。

项目最初只是一个展示 A 股涨停数据的前后端应用。经过多轮需求讨论、真实数据接入、Agent 架构重构、预测复盘、产品界面调整和生产部署，它已经形成一个可以本地运行、通过域名访问、持续积累研究数据的首板评级与复盘 Agent。

V1 的核心成果不是“做出了一个能够准确预测股票的模型”，而是建立了一套完整、可解释、可回放的研究闭环：

```text
真实市场数据
  -> 首板候选过滤
  -> 结构化 Facts
  -> 版本化评分
  -> Agent 工具问答
  -> 每日 Top10 快照
  -> D+1 至 D+5 走势回填
  -> 预测复盘与质量审计
  -> 评分策略改进建议
```

系统始终定位为研究工具，不构成投资建议，不提供买卖指令、仓位、目标价或收益承诺。

## 2. 产品定位的演进

V1 经历了几次重要的需求收敛。

### 2.1 从涨停看板到首板研究工具

早期项目主要展示涨停股票和市场概况，差异化有限。后来我们将核心问题聚焦为：

```text
当日收盘后，哪些首板股票的结构质量更值得继续观察？
```

系统因此不再追求覆盖所有量化交易场景，而是围绕首板候选、评分解释、次日晋级和后续走势建立产品能力。

### 2.2 放弃集合竞价作为核心输入

一进二场景最初考虑接入次日集合竞价，但真实竞价数据存在稳定性、时效性、授权和历史回测困难。V1 最终选择收盘后研究场景，优先保证数据可验证、评分可回放和结果可复盘。

### 2.3 明确 LLM 与确定性代码的边界

LLM 不直接计算原始评分，也不能凭记忆补造市场数字。

- 确定性代码负责候选过滤、Facts 构建、评分、统计和结果回填。
- LLM 负责理解问题、规划工具、组织解释、发现风险和总结复盘。
- Tool Policy 和 Query Contract 负责约束模型，确保需要市场事实的问题必须调用对应工具。

这一边界让项目真正具备 Agent 工程价值，而不是简单地给行情页面套一层聊天框。

### 2.4 主动删除低价值功能

历史相似案例曾经是重点功能，但相似度定义难以验证，计算成本较高，对推荐和解释的增量价值有限。V1 已将其从产品范围中删除。

完整账号系统也曾实现过一版，但考虑首版上线节奏、邮件服务、OAuth 配置和运维成本，最终回退为匿名访客隔离。V1 用户可以直接体验完整功能，同时会话、限流和用量仍按匿名身份隔离。

这些删除不是倒退，而是产品边界逐渐清晰的结果。

## 3. V1 已完成的产品功能

### 3.1 首页 Agent 对话

首页以 Agent 对话为核心入口，而不是把聊天功能藏在边角位置。

用户可以询问：

- 最新交易日全部首板、连板、炸板和涨停股票。
- 指定日期、板块、题材、板高和市场范围的股票集合。
- 哪些首板候选评分靠前，以及高分或低分的原因。
- 某只股票近期 K 线、首板位置和龙虎榜情况。
- 近一周主要指数走势，以及本地涨停数据中的行业和题材分布。
- 每日连板晋级率、首板到二板成功率和高分 Top10 的实际表现。

股票名称会转换为可点击链接，用户可以直接进入个股详情。

### 3.2 盘前推荐

盘前推荐页面展示最新交易日的首板评级 Top10，作为次日观察候选。

每个候选包含：

- 股票基本信息、行业和题材。
- 总分、评级和置信度。
- 评分拆解、主要理由和风险。
- 上板形态、市值偏好和首板位置判断。
- 评分所依据的数据完整性。

推荐代表研究优先级，不代表交易指令或确定性预测。

### 3.3 复盘

复盘页面围绕预测结果和市场接力情况组织内容：

- 最近 5 个交易日的连板晋级率。
- 可点击查看每日晋级成功股票。
- 每日预测 Top10 到最新收盘的 D+1 至 D+5 走势。
- Top10 首板到二板成功率与当天全部首板成功率对照。
- 表现较好和较差股票的排序、题材、市值及首板位置特征总结。
- 主板和创业板龙虎榜股票展示。

复盘不再只是展示涨跌，而是尝试回答评分在哪些样本上有效、在哪些样本上失效。

### 3.4 涨停池

涨停池承担结构化数据库入口的作用，覆盖：

- 首板票。
- 连板票。
- 未回封炸板票。
- 近三日涨停股票。

用户可以从列表进入个股详情，查看封板信息、60 日 K 线、日内分时、首板位置、龙虎榜和可用的评分证据。

### 3.5 会话管理

Agent 已具备接近常见聊天产品的会话概念：

- 新建、恢复、重命名和删除会话。
- 页面刷新后继续历史对话。
- 会话和消息持久化到 SQLite。
- 不同匿名访客之间的数据隔离。
- LLM 上下文只取受控的最近消息，避免无限增长。
- 流式回答时自动滚动到最新内容。

## 4. V1 已完成的数据能力

### 4.1 多来源真实数据

项目已经接入或封装以下数据能力。这里区分“代码中存在的数据适配器”和“V1 Agent 默认可调用的数据”：

- AKShare 涨停池、炸板池、交易日历和历史行情。
- 同花顺涨停池、热股榜、龙虎榜、行业和特色数据。
- 东方财富人气、龙虎榜、行情和公开资讯。
- 腾讯日内行情快照。
- 巨潮资讯上市日期和公司基础信息。
- 公开财经新闻、公告和网页检索。

V1 默认只使用已经落库、具备明确交易日截止点的完整收盘数据。热股榜、实时板块、远端涨停池、财经新闻和网页检索适配器保留给 V2 研发，不进入 V1 默认 Agent 工具集，也不参与 V1 首板评分。

所有外部来源都允许失败降级。关键字段缺失时写入 `data_missing` 或健康报告，不使用看似合理的默认数字掩盖缺口。

### 4.2 首板候选池

V1 候选池只保留收盘封住的首板，并执行以下过滤：

- 排除 ST 和退市风险警示股票。
- 排除北交所和科创板。
- 排除新股和次新股。
- 排除成交额过小、流动性不足的样本。
- 缺少关键过滤字段时降低置信度。

### 4.3 结构化评分输入

评分目前综合使用 14 类信息：

1. 首封时间。
2. 上板形态，一字板与盘中上板分开评价。
3. 封板稳定性和炸板次数。
4. 封板次数。
5. 换手率。
6. 成交额。
7. 行业和题材热度。
8. 市场接力环境。
9. 最近 60 日 K 线结构。
10. 板块强度与接力情况。
11. 流通市值偏好。
12. 近期涨停历史和股性。
13. 龙虎榜资金信息。
14. 市场人气快照。

评分输出包含 `score`、`rating`、`confidence`、`score_breakdown`、`reasons`、`risks`、`data_missing` 和 `scoring_version`。

### 4.4 首板位置判断

个股位置判断使用首板当日及以前的 K 线，不读取未来数据。当前可识别：

- 超跌反弹。
- V 形反转。
- 低位启动。
- 中位平台突破。
- 趋势加速。
- 高位震荡。
- 高位突破。
- 二波启动。
- 结构不明。

位置类型目前主要用于解释和复盘，没有在样本不足时直接改变评分权重。

### 4.5 每日预测闭环

系统保存每日 Top10 不可变预测快照，并持续回填后续真实走势：

- D+1 开盘、最高、最低和收盘表现。
- 是否晋级二板。
- D+1 至 D+5 K 线路径。
- 以次日开盘为基准的收益和回撤。
- 三日结果和预测评价标签。

每日任务使用交易日历、收盘时间门禁、文件锁、幂等检查和有限重试。只有当日收盘后生成的快照可以标记为 `live`，迟到补算只能标记为 `historical_backtest`。

V1 收尾阶段进一步增加了 D+1、D+3、D+5 成熟度核验。应成熟但未就绪的结果会使流水线标记为 `partial` 并生成告警，避免缺失数据静默进入评分审计。

## 5. V1 已完成的 Agent 工程

### 5.1 工具调用主链路

当前问答主链路为：

```text
用户问题
  -> LLM Planner
  -> JSON 工具计划
  -> Agent Query Contract v2
  -> Tool Policy Engine
  -> 结构化工具执行
  -> Facts-first 回答 Prompt
  -> LLM 流式生成
  -> 输出清洗与股票链接
```

Agent 不依靠固定 Intent 模板接住所有问题。LLM 负责规划，确定性策略负责修复遗漏的必要工具和约束用户明确表达的查询条件。

### 5.2 Query Contract v2

Query Contract 统一解析和约束：

- 明确日期与默认最新交易日。
- 首板、连板、板高和炸板状态。
- 主板、创业板、科创板和北交所范围。
- 行业、题材和股票名称。
- 完整列表、计数、排序和 Top-N。

用户原始问题中的明确条件优先于 Planner 猜测，降低模型改写查询范围导致的错误。

### 5.3 工具体系

V1 已形成覆盖核心问答的工具层，包括：

- 本地涨停、连板和炸板事件。
- 首板评分、筛选、解释和 Critic 复核。
- 个股 K 线和首板位置。
- 主要指数区间走势和龙虎榜。
- 每日晋级率和首板到二板明细。
- Top10 追踪复盘、评分回测和 Evaluation。
- 预测质量审计、评分策略状态和数据健康。

默认 `v1_close_review` 配置会在 Planner Schema、Skill Registry、Tool Policy 和工具执行器四层使用同一白名单。`sector_performance`、`hot_stock_ranking`、`remote_limit_up_pool`、`finance_news` 和 `web_search` 仅在 `extended` 研发配置中启用。即使 Planner 错误生成这些调用，V1 执行器也会拒绝执行。

### 5.4 轻量 Multi-Agent

V1 没有采用多个模型无限对话的复杂编排，而是设置职责清晰的角色：

- Chat Agent 负责理解问题和组织回答。
- Facts Builder 负责结构化事实。
- Rating Engine 负责确定性评分。
- Explanation Agent 负责解释。
- Critic Agent 负责寻找反向证据和数据缺口。
- Review Agent 负责高分票追踪和市场对照。
- Evaluation Agent 负责历史预测评价和经验总结。

这些角色具有结构化输入输出，可以分别测试、缓存、追踪和替换。

### 5.5 流式输出与降级

- Agent 使用 SSE 流式返回回答。
- 前端只展示面向用户的最终文本，不暴露内部工具名称。
- Markdown 会被正确渲染，不再直接显示 `**` 等语法符号。
- LLM 超时、限流或不可用时，可以基于同一批工具事实生成确定性降级回答。
- 对无法取得可靠事实的问题，明确回答“抱歉，该问题无法回答”，不允许模型胡乱补全。

## 6. V1 已完成的评测与自我改进

### 6.1 不可变预测与结果评价

Evaluation Agent 会根据后续真实结果，将预测分类为成功、部分成功、失误、成功规避或漏选，并生成经验和评分改进建议。

这里的“自我评价”不是让 LLM 给自己的文字打分，而是用历史时点预测和未来真实结果进行可审计对照。

### 6.2 Champion 与 Challenger

评分策略采用版本化 Champion/Challenger 机制：

- Champion 是当前生效策略。
- Challenger 只在影子模式生成和验证。
- 权重调整有变化上限。
- 训练、验证和测试按交易日期顺序切分。
- 必须同时关注收益、晋级率和下跌风险。
- 样本不足时不能自动晋级。
- 策略切换必须显式批准。

因此，V1 实现的是受控改进框架，而不是宣称系统已经能够自主学习。

### 6.3 预测质量审计与快速证伪

系统可以区分 `live` 与 `historical_backtest`，并审计 Outcome 覆盖、评分版本和确定性基线。

单因子诊断按交易日计算横截面 IC，结合符号翻转检验、Bonferroni 校正、按日留一 Lasso 和日期块 bootstrap，避免把同一天大量股票错误当作独立时间样本。

目前最重要的诚实结论是：现有数据还没有证明评分策略具备稳定、可复现的预测优势。这个结论不会阻止系统积累数据，但会阻止我们过早宣传“预测准确”或自动修改线上权重。

### 6.4 自动评测

项目已经建立 Agent 回归评测集，覆盖：

- 常见涨停和首板问题。
- 指定日期、市场和板高条件。
- 个股走势、评分解释和市场指数。
- 完整名单和 Top-N 语义。
- 工具调用正确性。
- LLM 是否真实参与规划。
- Provider 抖动和后端修复率。
- 越界投资建议拦截。
- V1 实时能力越界问题和禁用工具注入拦截。

截至本次 V1 收口，完整后端自动化测试为 `254 passed`，另有 `6` 个 V1 范围评测子用例通过。

- 写冲突有限重试。
- 版本化 Schema 迁移。
- 并发初始化和读写测试。

- 生产环境强制使用足够长度且彼此不同的密钥。
- Agent 按访客、IP、每日额度和并发数限流。
- 记录真实 token 用量和可选成本估算。

### 7.4 生产部署

V1 已经部署到香港 Ubuntu 服务器，并完成：

- Docker Compose 编排前后端和每日任务。
- Nginx 反向代理。
- 域名访问和 HTTPS 证书。
- SQLite 持久化卷。
- 工作日收盘后自动更新。
- 数据库自动备份和日志轮转。
- 生产健康检查与失败报告。

项目已不只是“在开发机上能跑”，而是具备了第一版真实网站的运行形态。

## 9. V1 当前边界

V1 已经可用，但仍有明确边界。

### 9.1 评分尚未证明稳定有效

现阶段评分更接近“结构化研究优先级”，不能宣称具有稳定预测能力。高分票表现仍可能弱于简单基线，因子诊断目前没有发现稳健信号。

### 9.2 数据不是券商级实盘数据

当前数据适合收盘后研究和公开网站演示，不适合毫秒级实盘交易。公开接口可能限流、调整字段、延迟或暂时不可用。

### 9.3 V1 是单机架构

SQLite、进程内限流和单机 Cron 适合第一版部署。未来多实例扩容需要 PostgreSQL、Redis 和独立任务队列。

### 9.4 Agent 只回答 V1 数据边界内的问题

Agent 可以查询本地收盘数据、历史日 K、评分和复盘事实，但不回答实时行情、集合竞价、实时热榜、实时板块或最新新闻。越界问题统一明确告知无法回答，不能用旧数据、模型记忆或公开常识伪装成实时事实。

### 9.5 暂不提供正式账号系统

V1 使用匿名会话，适合低门槛体验。跨设备同步、收藏、自定义策略和个人数据需要正式账户体系支撑。

## 10. V2 工作展望

V2 不应继续无节制增加页面和 Agent 角色，而应集中提升预测闭环的可信度、Agent 回答质量和线上运行稳定性。

### 10.1 第一优先级：提高预测研究质量

- 持续积累真实 `live` Top10 预测和 D+1 至 D+5 Outcome。
- 建立按月、市场环境、题材、市值和位置类型分层的预测报告。
- 对比最早封板、低市值、固定随机等简单基线。
- 检查当前负向或不稳定因子，避免凭小样本直接反转权重。
- 扩展多口径 Outcome，分别关注次日开盘到收盘、晋级二板和下行风险。
- 只有样本量和样本外结果满足门槛后，才考虑晋级 Challenger。

### 10.2 第二优先级：提高 Agent 精准度

- 把真实用户失败问题持续加入自动评测集。
- 增强复杂组合查询和多工具计划的稳定性。
- 对日期、来源、完整列表和单位进行更严格的输出校验。
- 在 V1 固定收盘数据边界内完善日期、股票集合、评分和复盘回答。
- 建立线上匿名失败样本的脱敏归档和回归机制。
- 优化 LLM 首 token 延迟和工具并发，减少等待时间。

### 10.3 第三优先级：扩展 V2 实时与多策略能力

- 为实时热榜、板块、新闻和远端行情建立授权、时效、来源和失败降级标准。
- 在稳定数据源与独立 Eval 就绪后，再从 `extended` 配置逐项开放工具。
- 复用不可变预测快照、Outcome 和质量审计协议，增加其他短线研究策略。
- 实时能力不得反向污染 V1 的完整收盘数据口径。

### 10.4 第四优先级：增强数据流水线

- 为每个外部数据源建立成功率、耗时、最近更新时间和字段质量监控。
- 增加来源优先级、交叉校验和熔断策略。
- 对每日任务、Outcome 缺口、备份失败和数据过期建立主动告警。
- 将历史补算、每日更新和失败重试拆分为可观察任务。
- 继续保证不可变预测记录与历史回测结果严格分离。

### 10.5 第五优先级：生产架构升级

- 用户量增长后迁移到 PostgreSQL。
- 使用 Redis 实现跨实例会话辅助、缓存、限流和配额。
- 引入独立 Worker 处理数据采集、回填、评测和长任务。
- 增加正式账号体系、跨设备会话和用户配置。
- 建立 CI/CD、预发布环境、日志聚合、错误监控和自动回滚。

### 10.6 第六优先级：求职展示与产品包装

- 制作 3 至 5 分钟演示流程。
- 补充架构图、关键页面截图和短演示视频。
- 准备 Agent Query Contract、Tool Policy、预测闭环和并发治理的技术说明。
- 准备一个失败案例，展示系统如何发现错误、回填结果并阻止不可靠策略上线。
- 将 V1 的工程取舍整理成面试可讲述的设计决策记录。

## 11. V2 建议验收标准

V2 可以以以下结果作为阶段验收，而不是用“又增加了多少功能”衡量：

```text
1. 连续积累足够的真实 live 预测结果日，Outcome 缺口可观测且可追补。
2. 评分策略在样本外至少能稳定解释自己是否优于简单基线。
3. 核心 Agent 评测覆盖真实用户失败问题，并保持稳定通过率。
4. 关键数据源、每日任务、LLM 和成本均具备线上监控与告警。
5. 系统可安全迁移到多实例架构，并具备正式用户能力的实现方案。
6. 面试官可以在 3 至 5 分钟内理解项目的业务价值和 Agent 工程亮点。
```

## 12. 写在 V1 结束时

LimitUpLab V1 不是终点，也不是一个已经被证明可以预测市场的系统。

它真正完成的是基础设施和方法论：我们有真实数据，有可解释评分，有能调用工具的 Agent，有不可变预测，有未来结果回填，有反向证据，有自动评测，也愿意在数据不支持时明确说“当前没有可靠信号”。

从一个涨停列表，到一个通过域名访问、每天自动更新、能够持续评价自己的 Agent 产品，这就是 V1 最值得记录的进展。

下一阶段的重点不再是证明我们能堆更多功能，而是证明这个系统能够长期、稳定、诚实地积累知识，并在证据足够时做出更好的判断。
