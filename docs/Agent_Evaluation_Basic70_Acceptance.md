### 明确问题与最小证据

1. **LH-B003：长名单编造。** 真实post_limit_screen返回83只，前30名回答正确；回答将第31名列为600683京投发展，实际第31名为600691潞化科技，且600683根本不在83只中。后半段还出现多只不在证据中的股票和重复代码。证据：response.json内`ev_5616e55cc7f64963.payload.candidates`，以及answer的“第31–83名”。Judge输入149,609字符，超过当前最大支持值100,000，未运行；复核不能把not_run当pass，也无需再花Token确认已经可直接证伪的名单。
2. **OFF-B007：输出约束漏判。** 问题“只列代码名称和评分”，回答额外加入日期段与“来源：首板评级候选池…”。没有必须额外解释的安全/缺失例外，Judge的task_completion仍pass。OFF-B028的严格纯名单则确实只输出“600001 样例甲”。
3. **LH-B007：统计范围混淆。** 回答“当日首板评级候选池共58只”；证据里的58是universe_count，生产`app/agents/first_board.py`定义为len(latest_events)，不是过滤后的候选数。Judge未识别。不能把总体样本数当入选候选数。
4. **OFF-B009、OFF-B029：缺失原因推断。** 夹具只给出2个预测日、1日完整、覆盖率0.5，没有逐日成熟状态和缺失原因。回答把缺口确定归因为“次日尚未成熟”；OFF-B029还明确定位9月11日并承诺补数据后覆盖率自然上升。日期锚点可提供上下文，但不能替代缺失原因事实，需要专项裁决；暂不计通过，Judge的grounding pass仅保留原始意见。
5. **LH-B006：预期终态误杀。** 原始评级工具状态ok，但指定000636的candidates为空。用例据工具状态只允许complete/partial，Agent正确报告无记录并finish(empty)，被错判agent_failure。应根据业务结果而非工具ok自动生成终态合同。
6. **OFF-B014：终态争议。** 主要指数两项区间涨幅和“非逐日上涨”均已交付；Agent因缺少其他指数/逐日明细选择partial，用例仅允许complete。需明确问题是否要求完整指数集合；不能仅为了消除失败随意放宽所有终态。
7. **LH-B005：覆盖失效。** 问题只说“标的000636…近7个交易日完整样本数和样本质量”，没有说“高位回撤信号统计”。Agent合理地报告7根个股日K完整性，没有调用post_limit_statistics；Judge pass并不证明目标工具/能力已测到。
8. **LH-B009：审计范围含糊。** 问题只给日期和标的，没有明确start_date。Agent选择8月1日至9月11日，而基线录的是9月11日单日。补评Judge按文字问题判pass；需先明确窗口再定义期望，不应暗中要求固定参数路线。
